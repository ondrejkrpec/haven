Local development

Status: H0.5, verified locally on 2026-10-25. The foundation requires a POSIX shell, Git 2.28+ (git init -b) and sha256sum. Configuration validation needs Python 3.12+, system IANA time-zone data and hash-pinned Python dependencies. The complete check workflow also needs Node.js/npm and pinned Linux check binaries; see documentation and checks. Optional research reproduction needs Linux and rootless Podman. A VPS and paid API access are unnecessary for local work.

Separate the public project and each instance

Use a parent workspace such as project-haven with sibling Git repositories haven and haven-private. The parent is an ordinary directory. Maintained research evidence belongs in haven/research; disposable experiment directories belong under /tmp and are not required for development.

Clone the public repository into haven, then follow the setup block in README. It copies only templates/private to a new sibling directory, initializes an independent Git repository and creates config/instance.yaml. It refuses an existing destination. For another instance, use a different new directory name.

The copied template contains README, agent rules, ignore rules, a versioned YAML example and directories for personal instructions, runbooks and future encrypted secrets. Edit the copy. Keep the public example synthetic. The validator reads private files only when explicitly named; no Git submodule or private dependency is required.

Follow configuration v1 to install dependencies, validate the example or your private configuration, and apply explicit overrides. The file is Haven input, not native Hermes configuration. H1.4 supplies the separate subscription-provider renderer and explicit live preparation/probes. Public checks use synthetic inputs and never contact the host or model provider. Validation never needs real credentials.

The local private workspace was migrated from the unchanged H0.2 example to configuration v1. That initial migration used synthetic values; real installations subsequently maintain their own private configuration. The public template remains the source for creating another user’s workspace; changes to an existing private instance must be intentional and must not overwrite personal edits.

Work on a change

Use a focused local branch once project history exists. Review public/private boundaries, update the relevant guide and run checks appropriate to the change:

git diff --check
git status --short
(cd research/h0.1 && sha256sum -c SHA256SUMS)
.venv/bin/python scripts/validate_config.py examples/instance.yaml
.venv/bin/python -m unittest discover -s tests -v

The checksum manifest covers the retained H0.1 report, pins, patch, MIT notice, probes and sanitized evidence. It detects accidental changes; it is not a signature. The behavior suite checks configuration and public documentation boundaries; it does not run Hermes or paid services. After installing the H0.4 check tools, run .venv/bin/python -m scripts.check for the full local/CI workflow. The first GitHub run was attempted; automatic local push checks replace unavailable Actions, recorded in H1.1.

Primary branch and merge policy

The default branch is main; the repository has not been renamed to master. The active owner-only ruleset restricts creation, updates and deletion of the default branch, main and master. Its only bypass actor is user ondrejkrpec (GitHub user ID 8884243), with no role-wide, team or application exception. This also prevents another writer from merging pull requests into those branches.

The owner can push directly or merge reviewed changes. Coding agents, including Codex or a future Nora integration, may merge pull requests through the owner account within work authorized by the owner. Prepare changes on topic branches, validate against the current target branch and confirm that the PR head still matches the checked revision before merging. A GitHub API or web merge does not invoke a local pre-push hook, so the merging agent must perform those checks explicitly. Direct primary-branch commits or pushes by an agent need an explicit owner request. This policy does not grant general production autonomy.

The server rule controls the authenticated GitHub actor, not a commit’s author field. The owner account already permits both human and delegated-agent merges; no additional bypass role, bot account or application is needed for that identity. Future Nora credential delivery remains implementation work. Lower-trust coding executors must not receive the owner’s credentials; keep any delegated merge operation on the trusted side of the controller/executor boundary.

This server-side access rule is independent of GitHub Actions and complements the local pre-push checks. It was read back from the ruleset API and the effective rules for main on 2026-10-25. The only repository collaborator at verification was the owner. See GitHub’s restriction semantics and individual-user bypass support.

Optional H0.1 reproduction

The complete historical procedure and its limitations are in the research report. It builds Hermes through its own pinned package manager and uses the upstream test runner. This can download substantial dependencies and images; it is separate from foundation setup.

Never reuse an active Hermes home, runtime or Podman store for an experiment. Do not supply real credentials. The report uses disposable paths and synthetic provider responses. Rootless probes still execute container processes; they do not establish production security on Ubuntu.
