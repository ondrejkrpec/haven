Wishlist: first direct-fetch feasibility check

Status, 2026-11-06: workstation and read-only VPS feasibility. One of three owner-supplied product pages returned usable structured data from the workstation; two returned usable data from the VPS. The third returned HTTP 403 from both origins. The source mapping, personal URLs and local captures remain private. No wishlist service, schedule or model-enabled Telegram operation was deployed.

Method and scope

Source baseline: 1e689a1d59549e618a20e3e34bcb9a6089ce17d7. The probe implementation is identified by its source hashes in the sanitized receipt; no self-referential commit hash is stored. The receipt is a measurement record, not a CI success or production acceptance.

The operator explicitly supplied three HTTPS product URLs outside public sources. A temporary Python standard-library runner issued one unauthenticated GET per source with user agent HavenWishlistFeasibility/0.1, no cookie jar or proxy inheritance, TLS verification, a 20-second socket timeout, a 4 MiB body limit and redirects restricted to the explicitly named HTTPS hosts. The enclosing process had a 55-second deadline. No JavaScript, model, browser session or account login was used. Raw HTML and full source identities stayed outside public Git/build inputs.

This demonstrates why workstation egress alone is insufficient. It establishes one successful direct extraction for two sources in the intended host environment, not a supported daily service or independently verified promotional conditions.

Repeatable offline extraction

scripts/wishlist_extract.py reads a saved response and its original HTTPS URL/status. It performs no network requests or model calls. It selects exact-offer structured data from scoped Product microdata or JSON-LD, preserves variant/query identity, uses decimal money and returns a candidate. It rejects conflicting prices, ambiguous identities, aggregates, unsupported conditions and missing data. It does not execute scripts, follow remote JSON-LD contexts or trust an unrelated recommendation’s cheaper price.

With an explicitly reviewed response stored outside the repository:

.venv/bin/python -m scripts.wishlist_extract \
  --html "$WISHLIST_CAPTURE_FILE" --url "$WISHLIST_SOURCE_URL" \
  --http-status "$WISHLIST_HTTP_STATUS"
.venv/bin/python -m unittest tests.test_wishlist_extract tests.test_wishlist_contract -v

Exit zero means extracted, not "verified deal". Every candidate carries conditions_verification=not_verified. Other results are blocked, unavailable or needs_review, with fixed reasons and no raw exception/source text. HTTP 401/403/429 is handled before parsing; an error page must not become a zero or stale-new price. UTF-8 capture and two-decimal positive prices are the current probe’s bounded subset, not universal shop/currency support.

The 18 synthetic extraction/contract tests passed on Python 3.14.7 and in a fresh Python 3.12.14 environment using the existing hash-pinned runtime dependencies. The minimal dependency set does not register JSON Schema date-time validation automatically; the contract helper supplies a checker for real calendar dates and explicit UTC offsets. Tests deliberately demonstrate that valid JSON shape can still contain an unauthorized owner context or private fetch destination: those denials belong to the future service, not this probe.

The live runner is deliberately not a production collector. The future client still needs pinned public destinations, safe redirect/DNS handling, retry-after/backoff, cancellation and current-run authorization. Repeated collection, sustained source access and promotional-condition verification remain unverified.

Decision for the first implementation

Proceed with independent link intake and collection status so blocked sources do not delay durable wishlist data. Start adapters with the two directly demonstrated structured-data paths, then verify repeated collection and shop conditions. The owner subsequently requested browser experiments: true headless modes stayed blocked, while ordinary Chromium accessed the third product both on the workstation desktop and on Xvfb. VPS browser access and price-condition validation remain pending; no production browser infrastructure was added.

The concrete interface proposal defines command shapes, owner binding, receipts, clarification, collection admission and implementation units. Actual service behavior, transport security, database restore and Telegram acceptance are future work.

References: Python 3.12 urllib, HTMLParser, Schema.org Offer and the pinned Hermes admission hook. Context7 had no Python 3.12-specific version; the matching official Python documentation was used for that version. The pinned Hermes hook remains fail-open, so the independent guard remains necessary.
