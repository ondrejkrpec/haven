H1.6: private Telegram text

Status, 2026-10-29: accepted on the existing Ubuntu pilot. Private bot enrollment, owner text replies, denied-sender intake, remote-command restriction and enabled-transport restart recovery are verified. The owner selected Telegram for themselves only after confirming WhatsApp Agent Platform is unavailable on their account. Voice, the second member and family data remain outside this text milestone.

Bounded pilot

Hermes stays at v0.22.5, base bf0203a794a07aac3ff764972ab9087baa4e4f4e, with the existing attributed recovery patch. The native Telegram extra pins python-telegram-bot[webhooks]==22.8; the pilot uses only long polling. There is no public webhook, new firewall rule, third-party plugin or second gateway.

The optional Haven input is telegram.enabled and a quoted numeric telegram.owner_id. Disabled is the default; enabled requires exactly one owner. A username/display name is not an identity. The native profile has matching sender/private-chat allowlists, a nonmatching group sender sentinel, no guests/bots/group observation and no remote administrative principal. The permitted chat commands remain help/whoami/new/stop/status. Native Telegram intake rejects strangers and groups before event construction; the command gate and model tool restrictions remain separate.

CLI/local/API/cron/Telegram/WhatsApp model toolsets are empty. Coding dispatch, fallback, MCP/hooks, community plugins and lazy installs stay disabled. Automatic speech transcription is off; full attachment behavior and Czech voice quality are not accepted here. Strict outgoing media paths do not trust fresh arbitrary host files. Cold boot does not deliberately discard pending Telegram updates; this is not an exactly-once message-delivery guarantee.

The service explicitly disables first-contact profile building and predeclares the busy/tool-progress hints as seen. Those native hints otherwise write onboarding.seen into the guarded YAML after a message. They offer settings/tools outside this pilot, so they are suppressed rather than allowing arbitrary runtime configuration edits. The first-contact regression test exercises the actual pinned handler and confirms that the rendered profile remains unchanged.

Prepare without activating

Use the checked public commit, pinned Ansible dependencies and explicit private inventory from H1.3:

export ANSIBLE_CONFIG="$PWD/ops/ansible.cfg"
export ANSIBLE_HOME="$PWD/build/ansible"
.venv/bin/ansible-playbook -i ../haven-private/ops/inventory.yml \
  ops/telegram-prepare.yml -e haven_telegram_prepare_authorized=true

This checks the exact source and dependency hashes, builds /var/lib/haven/telegram/venv through upstream PM with only --extra telegram, verifies the real 22.8 import and protects prepared code as root-owned/read-only. Installation HOME/profile/cache are separate from production credentials. It neither changes the core environment nor enables messaging. The receipt permits repeat preparation with the same pins.

Render/deploy the updated service with both transports disabled using the application procedure before owner enrollment. The guard/helper/pin files belong to the bounded application snapshot; credentials, conversations and databases do not. The selected interpreter changes to the prepared Telegram environment only when Telegram is enabled. A missing model login still does not stop deterministic scheduling; an enabled messaging transport requires its own protected credential file.

Owner enrollment

  1. Create a bot through official BotFather using /newbot. Keep the token private; do not put it in YAML, command arguments, chat or Git.

  2. In the owner’s own terminal, run the installed helper over interactive SSH. It requires the disabled Telegram profile and refuses an existing token:

ssh -t haven-example 'sudo -u haven /usr/bin/env \
  HERMES_HOME=/var/lib/haven/.hermes PYTHONPATH=/var/lib/haven/haven-tools \
  /var/lib/haven/telegram/venv/bin/python -m scripts.telegram_runtime enroll'

The helper prompts for the token without echo, verifies the bot and refuses an existing webhook. It prints a random one-time challenge in that local terminal. Send that exact text to the displayed bot from your own Telegram account. Only a matching challenge in a human sender’s private chat can select the numeric owner. The helper saves the token in /var/lib/haven/.hermes/credentials/telegram-bot-token with directory 0700 and file 0600, then prints only the verified owner ID and bot username. It neither calls the model nor sends chat messages. Keep other pollers stopped throughout enrollment.

Enter that ID in the private instance, render a fresh --service profile and deploy explicitly:

schema_version: 1
telegram:
  enabled: true
  owner_id: "123456789" # synthetic; use the locally verified owner ID
whatsapp:
  enabled: false

Do not reuse the synthetic ID. Startup validates policy, dependency hashes and credential metadata, then reads the token into a sanitized child environment. Native YAML and application rollback never contain it. Health requires the running gateway, fresh heartbeat and a connected Telegram adapter from the same process.

Live acceptance

  1. Send a unique harmless text from the owner’s private chat and verify one Nora answer without tools/fallback.

  2. Verify a denied principal cannot reach conversation/model handling. A separate account is optional: temporarily configure a different valid numeric owner ID, send from the now-denied actual owner, check connection plus aggregate session/model counters, and restore the accepted profile in cleanup even on failure.

  3. Verify admin commands cannot change models/configuration or run tools. Do not confuse a hidden command menu with authorization.

  4. Restart the managed service, verify it reconnects without token entry and send another unique text. Inspect replay/duplicate handling without assuming exactly-once external sends.

  5. Repeat deployment unchanged and retain a working application rollback. Never copy/delete the token or OAuth as a rollback step.

Do not run a second unmanaged gateway or getUpdates poller beside the service. After uncertain delivery, reconcile before resending. Revoke/rotate compromised bot tokens through BotFather with a deliberate disabled-profile replacement; enrollment refuses silent overwrite.

Local evidence and reproduction

The foundation suite covers schema rejection, bounded runtime policy, token permissions/symlink rejection, supervised token injection, private-challenge enrollment and fixed diagnostics. Full public checks also run production Ansible lint/syntax, secret scans and the documentation build/links.

A separate fresh test environment was built through the exact upstream PM lock with --group dev --group test --extra telegram. The previous H1.5 environment lacked PTB; the first research run failed two cases for that missing dependency. The original complete run passed 81 tests. Adding the first-contact regression brings the selection to 82 passing tests across nine files, with no retries; five are retained Haven scenarios and the rest are upstream tests. No live account, model or production profile was used in these test runs.

From the pinned patched Hermes checkout, set HERMES_PYTHON to that disposable interpreter and HAVEN_ROOT to the public Haven checkout:

HERMES_TEST_FILE_RETRIES=0 scripts/run_tests.sh -j 2 \

  tests/gateway/test_telegram_auth_check.py \

Future WhatsApp migration

The owner wants to reconsider WhatsApp next year; no availability date or automatic migration is scheduled. Keep the same coordinator/model/instructions and canonical domain data. Review the then-supported adapter and permissions, map the authenticated owner explicitly, enroll credentials separately and accept the new channel before disabling the old intake. Telegram/WhatsApp histories have different native session identities and are not silently merged. Decide history retention and reconcile queued/outbound work at cutover. The second member and family authorization need their own acceptance.

Existing pilot preparation

The application was prepared from public implementation revision 0d8c0551a0ef9fde26098ba0f5fdfd35aab668e6. Frozen dependency preparation passed; repeating it made no changes. The service guard/helper/unit were deployed with both messaging transports disabled, and the repeat made no effective changes. The actual PTB import and source-pin helper check passed. Noninteractive enrollment was refused before token entry or API use.

A separate application rollback check appended a harmless comment to the deployed Telegram helper, then restored all nine fixed files with their hashes, modes and owners. Service health passed afterwards. OAuth inode/size/mtime were unchanged across preparation/deployment and rollback. The baseline core interpreter remains selected until Telegram activation; the prepared optional environment is retained read-only. No OS update, firewall change, bot enrollment, live Telegram message or model request was performed by these preparation checks.

These initial results establish the application preparation path. The subsequent live acceptance below uses the enrolled account.

Live pilot result

The first enabled deployment connected and delivered a no-tools reply, but native first-contact onboarding wrote onboarding.seen.profile_build_offered into YAML. The strict guard rejected that unexpected field and automatic application rollback restored healthy disabled service. The first-contact regression reproduced the write; the explicit onboarding settings described above fixed it without relaxing policy comparison. The corrected application deployed from 191849494b5417129306b95703b2277470b4ac7e.

A controlled restart of the enabled service reconnects without token entry. The owner confirmed the subsequent synthetic reply.

The same enabled profile passed ok=19 changed=0 failed=0; the service stayed healthy under the same process without a restart.

Read-only acceptance audits selected only Telegram rows and returned aggregate counts or synthetic-marker matches, never transcripts or credentials. Local checks cover 75 project tests and 82 pinned native Telegram tests; live outcomes are separate evidence. This accepts one owner’s text pilot, not exactly-once external delivery, speech or a multi-user family authorization service.
