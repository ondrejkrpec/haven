H1.6.1: Explicit deterministic operations

Status, 2026-10-30: accepted on the Ubuntu pilot. Owner replies/refusals, zero model usage, rollback, idempotent repeat, restart and synthetic native boundaries are verified. The owner selected a deterministic capability profile in place of ordinary AI conversation. H1.6’s owner allowlist, protected Telegram token and native long polling remain the transport boundary. Voice and coding dispatch remain disabled.

Supported behavior

system.status (also stav systému) checks the current gateway PID, fresh heartbeat and connected Telegram writer. system.capabilities (also co umíš) lists enabled operations. Matching accepts case/spacing differences and final question marks, periods or exclamation marks; it never asks a model to classify intent. Other requests receive a fixed refusal. wishlist.check_deals is explicitly disabled and has no implementation.

The text usability update adds explicit natural Czech questions, including Jaký je stav systému?, Jaký je aktuální stav systému?, Jak se má systém?, Jak je na tom systém?, Co všechno umíš? and Jaké máš funkce?, with unaccented equivalents. Capability replies show Czech examples. The whole normalized message must match an alias; a quoted question, negation or appended instruction is not a match. This source update does not establish live deployment or enable transcription; H1.7 voice is deferred by the owner.

Both enabled operations have a zero model-call, token and monetary budget and a limit of 60 accepted requests per owner/operation/hour. The registry is deployment input, not chat-editable configuration. Enabling a future integration requires implementing its handler and authorization and accepting its effects separately. The current validator rejects nonzero model budgets and unknown handlers.

The ordinary --service renderer retains the accepted H1.6 AI chat. The explicit --service --capabilities combination selects this narrower profile. The two are intentional operator choices; never infer the active mode from a branch name.

Independent host enforcement

The trusted same-PID launcher validates the bounded native profile, exact patched Hermes source hashes and the two declared plugin files before arming an irreversible process policy. It then loads Hermes. The native patch gates agent construction, synchronous/asynchronous auxiliary LLM calls, both tool-dispatch boundaries and cron execution before scripts or external workers can start.

The post_gateway_admission plugin implements deterministic replies and audit. Hermes deliberately treats a missing, throwing or malformed consumer hook as fail-open. The independent native gates still refuse model/tool execution in that case. An audit failure also produces a fixed unavailable reply, never an AI fallback. A missing or altered deployed plugin/source fails startup with exit 78.

This is a bounded application policy, not an isolation boundary against arbitrary Python code or the service administrator. Other independently started interpreters do not inherit the latch. No lower-trust executor is enabled; H2 still owns that isolation. Native informational slash commands retain H1.6’s existing access policy and are outside this capability audit.

Private audit and replay

state/capability-audit.sqlite3 lives in the private Hermes home, with directory 0700 and database 0600. It contains hashed actor/request identity, request hash/byte length, operation, decision/reason, fixed reply/result, policy version/hash and zero usage/cost counters. Raw request text, Telegram IDs and credentials are not stored there. Unsalted hashes are pseudonymous metadata, not anonymization.

An immediate SQLite transaction serializes rate checks, execution and the receipt. A repeated transport message ID with matching text returns its stored reply, including after restart; conflicting reuse is refused. Handler authorization is repeated independently, before replay and at the handler boundary. Receipts expire after 30 days on a subsequent audited operation; the 50,000-row ceiling refuses further work until maintenance/retention frees space. SQLite secure deletion is enabled for removed rows; no claim is made about storage snapshots or backups.

The two handlers are read-only. Receipt replay does not guarantee exactly-once Telegram delivery and does not authorize future non-idempotent operations. Invalid intake rejected by native authorization is outside this post-admission database; an unavailable audit cannot record its own failure reliably.

Deploy and restore

Use checked, committed public sources and an explicit private inventory as in service deployment. No OS package, access, account or firewall change is needed.

export ANSIBLE_CONFIG="$PWD/ops/ansible.cfg"
export ANSIBLE_HOME="$PWD/build/ansible"
umask 077
capability_dir=$(mktemp -d)
.venv/bin/python -m scripts.render_model ../haven-private/config/instance.yaml \
  --service --capabilities --output "$capability_dir/config.yaml"
.venv/bin/ansible-playbook -i ../haven-private/ops/inventory.yml ops/service.yml \
  -e haven_service_authorized=true -e "haven_model_config=$capability_dir/config.yaml"

The application snapshot now also includes the fixed capability modules/configuration/plugin files and six native patch targets. It never copies the audit database, conversations, OAuth or Telegram credentials. The exact base hashes and patch checksum must match before the coordinator is stopped and the patch applied. Repeating a matching deployment does not reapply the patch or restart the service. Unknown drift in these patch targets fails closed.

For rollback use the new snapshot taken before this operation with the matching scripts/service_snapshot.py. Restore returns code/configuration and active/enabled state, and removes an empty newly introduced instance plugin directory. Older nine-file snapshots remain readable for their historical scope; they do not cover H1.6.1’s additional files. Do not use them to undo this upgrade. The audit database remains private and is not discarded by application rollback.

Local acceptance

Public behavior tests exercise exact-operation matching, zero budgets, owner/transport checks, replay/conflict handling after recreation, rate/capacity limits, audit permissions/corruption, source/plugin drift and guarded launcher selection. The public check pipeline never contacts the VPS, Telegram or a model.

The research test research/h1.6.1/test_native_capabilities.py runs fresh subprocesses through the real pinned Hermes APIs. It verifies agent/auxiliary/tool/cron refusal, an irreplaceable host latch, fail-open hook failure with the model still blocked, and actual plugin discovery plus a deterministic reply. Run from the pinned patched checkout with the PM-prepared test interpreter:

HERMES_TEST_FILE_RETRIES=0 scripts/run_tests.sh -j 2 \
  "$HAVEN_ROOT/research/h1.6.1/test_native_capabilities.py" \
  tests/gateway/test_post_gateway_admission.py tests/cron/test_restart_safe_worker.py

Use the existing PM environment with --group dev --group test --extra sms for these native core tests (aiohttp is required by the upstream webhook case). The separate --extra telegram environment covers the retained H1.6 Telegram tests. An initial run used the Telegram-only environment and failed the webhook case for missing aiohttp; it was rerun with the declared SMS extra. A sandbox-only runner attempt failed before collecting tests due to its read-only filesystem; neither failure is counted as a pass. No dependency was installed into production for these tests.

Live acceptance

The first deployment from merge cd4ce7711673e416d8b2d4ed55d5cedb5588cdb9 passed (ok=28 changed=10 failed=0). A real rollback to the accepted H1.6 restored all 26 application files, including content hashes, owners/modes and absence of newly introduced files; the original service passed health checks. The same H1.6.1 profile was then selected again.

A separate synthetic profile on the Ubuntu pilot, using its existing Telegram interpreter, blocked all seven actual agent/auxiliary/tool/cron entrypoints and recorded seven denials. Its temporary state was removed; it never started a gateway or used real credentials. Local verification comprises 88 public tests, 49 pinned native core tests and five retained Telegram scenarios.

The repeated active deployment passed ok=25 changed=0 failed=0, retaining the same live process. A subsequent controlled restart returned a new healthy gateway/connected Telegram and retained the audit database inode and existing receipts. No token entry was needed.

Read-only Telegram aggregates show no additional native model calls or conversation rows during deployment/rollback/restart; the new capability usage counters remain zero. Telegram token metadata is unchanged. OAuth-store metadata changed during service starts; its contents were not inspected, copied or restored. A zero model-call count does not assert zero OAuth/catalog networking.

The owner sent system.status, system.capabilities, wishlist.check_deals and HAVEN_H161_DENY_1 as separate Telegram messages and confirmed both expected replies and both refusals. Read-only audit found exactly two allowed explicit operations, one disabled-capability refusal and one unknown-operation refusal matching the synthetic marker hash. All capability model/token/cost counters are zero; native Telegram API-call and conversation-row aggregates are unchanged. The status request occurred after the controlled restart, confirming the real transport’s return. This accepts the bounded owner-text profile; future integrations, voice, family data and isolated executors need their own acceptance.
