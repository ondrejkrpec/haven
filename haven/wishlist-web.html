Wishlist web

Historical first delivery, 2026-11-18: a local, responsive interaction preview implemented the confirmed owner flows using synthetic data. That standalone preview is not connected to the pilot, its database, Telegram, shop fetchers or model credentials. The production implementation follows below; deployment and live acceptance must be recorded separately. Spending/savings dashboard requirements are deliberately unfinished; the UI labels that area as pending rather than displaying invented totals.

Run and review

Use the existing local Python environment and Node.js versions documented in local development. No new dependencies or build step are required:

.venv/bin/python -m scripts.wishlist_web_preview --port 8765

Open http://127.0.0.1:8765/. The preview serves only six explicitly allowed UI files from web/wishlist, binds IPv4 loopback, checks the Host header, refuses symlinks and sends a restrictive Content Security Policy. It does not serve a checkout, directory listing, neighboring private files or a general HTTP API. This development server must not be exposed as a production service.

Data stays in the current browser’s local storage under a versioned preview key. All seeded names, shops and prices are synthetic; shop links use reserved example domains. Added URLs are saved locally without fetching them. No telemetry, remote fonts, image downloads or external scripts run. The preview reset is reversible within the current session. Storage failures are visible; the browser is not a production backup or authority boundary.

Implemented interactions

  • Category groups, descending percentage/absolute price advantage within groups, name search and shop/category/availability/purchase-mode/lifecycle filters.

  • Default active view includes unavailable items and recurring items with muted notifications. Purchased one-time and removed entries have explicit filter views.

  • Desktop table and compact mobile rows; a modal side panel becomes full-screen on mobile. Keyboard focus, modal escape/close, field labels and live announcements support normal keyboard use.

  • Detail with immutable shop link, availability, successful-check/addition dates, editable name/category/mode/note, and month/90-day/year/all-history chart. The chart defaults to 90 days and offers an underlying daily-price table. Missing dates are gaps, not fabricated prices. Optional product images are not included in this version.

  • Purchase form uses a per-unit price, integer quantity and editable purchase date, showing the total before confirmation. Item detail lists purchases with correction and cancellation. Stale lifecycle cancellation is refused rather than overwriting a newer state.

  • One-time purchase leaves the active view. A recurring purchase mutes notifications for approximately 30 days, keeps its entry active and preserves price history. The remaining-days icon can restore notifications immediately. No actual notifications or collector run in this preview.

  • Removal is immediate and reversible through an undo notice or removed-items filter. Restoring a purchased entry does not reopen it.

  • Collection failure retains an explicitly dated last known price and labels its comparison. Verified unavailability without price hides the current price/comparison but preserves historical data.

  • The manual price-check control explicitly reports that live collection is not connected. It never invents a price or reports a successful fetch.

Price and purchase calculations

Money uses integer halere. For the inclusive 90-day Prague calendar window, average all valid prices within each measured day, then equally weight those daily means. Missing days contribute no value; the first real price immediately establishes both average and minimum. Minimum uses the lowest individual price observed in the window. Displayed reference means round to a haler.

Capture the reference mean available at the purchase date. Historical purchases exclude later calendar days, including across Prague DST changes. Savings per purchase are (reference mean - paid unit price) * quantity; overpayment is negative. Later observations cannot rewrite the saved reference. Amount/quantity corrections preserve that reference; changing the date recomputes it from that date’s available history. Purchases without any known reference remain explicitly unknown, not zero savings.

The standalone preview model does not change existing domain behavior: the pilot still uses its original classification and pause/collection semantics. Unifying those behaviors requires a separately tested domain change before production integration. Local lifecycle revision checks are interaction guards, not server authorization or distributed concurrency control. Concurrent browser tabs receive a change warning; they are not a synchronized database.

Validation and remaining scope

node tests/wishlist_web.test.mjs
.venv/bin/python -m unittest tests.test_wishlist_web -v

The model tests cover first-price averages, daily weighting and gaps, money precision, stock/failure distinctions, purchase references and backdating, DST boundaries, notification-only muting, correction/cancellation and reversible removal. HTTP tests cover the asset allowlist, response headers, Host denial and symlink refusal. Browser acceptance should exercise desktop/mobile flows and storage reloads; synthetic checks do not establish production authentication or live shop behavior.

Before production work, finish dashboard statistics (filter scope, historical purchase categories and past-period controls), review the first UI, settle access/write authentication and the URL under the existing private Haven origin, and define service boundaries, migrations, retry/idempotency and acceptance. Keep the existing domain as the sole production writer. Do not expose its ingress socket or reuse Telegram identity claims from a browser. Wishlist integration and Nora wording must share the resulting domain contract. Alza remains the final separate wishlist item; the final Haven security/architecture audit still follows the completed wishlist.

Production integration, 2026-11-18

The production adapter adds scripts/wishlist_web_domain.py, a dedicated peer-authenticated endpoint in the existing domain process, and scripts/wishlist_web_gateway.py, a network-isolated HTTP adapter. ADR 0019 records authentication and isolation. These implementation and synthetic results are distinct from live pilot acceptance.

The production page uses same-origin requests at /wishlist/api/command; it never reads demonstration local storage, falls back to sample products, or writes a second database. Reads are bounded and paginated. Mutation request IDs survive uncertain responses and re-bootstrap; the domain commits changes, events and receipts atomically, with version conflicts and signed owner-bound cursors. Tests include discarding the HTTP response after a committed recurring purchase, then retrying the same request ID without creating a second purchase.

Price means use equally weighted Prague calendar days, including the first observation. Persisted purchase references remain fixed when later prices arrive. Original purchase rows without a paid amount stay unknown; cancellation cannot guess an undocumented prior lifecycle. Legacy purpose/recipient fields remain as history but no longer block new intake. Recurring purchases mute notifications for approximately 30 days while daily collection continues. A manual refresh respects host backoff and a ten-minute per-offer minimum; the dedicated path unit wakes the existing bounded collector, with the timer as fallback. No offer notifications or cross-shop recommendations are added by this integration.

Prepare and install

Build an independent dependency artifact; do not replace the JSON Schema or native Hermes environments:

.venv/bin/python -m scripts.wishlist_dependencies build \
  --directory /absolute/path/to/http-artifact --requirements requirements-web.txt
.venv/bin/python -m scripts.wishlist_dependencies bundle \
  --directory /absolute/path/to/http-artifact --requirements requirements-web.txt

Take and verify a fresh backup with the existing controller. Then use the explicit private inventory and private owner configuration:

ANSIBLE_CONFIG=ops/ansible.cfg ANSIBLE_HOME=build/ansible \
  .venv/bin/ansible-playbook -i /absolute/path/to/private/ops/inventory.yml \
  ops/wishlist-web.yml -e haven_wishlist_web_authorized=true \
  -e @/absolute/path/to/private/ops/wishlist-web.yml \
  -e haven_wishlist_web_dependencies=/absolute/path/to/http-artifact

The private variables name haven_wishlist_web_origin (the existing HTTPS origin) and haven_wishlist_web_owner_login (the exact owner Tailscale login). The playbook installs and resumes services under shared maintenance exclusion, checks that the last backup is accepted and under two hours old, snapshots only declared code/configuration files, installs compatible backup helpers first and arms durable resume journal version 3 for the collector timer and three existing writers. Recovery runs while the same lease is held, then releases the lease even on failure. Failed resume intent remains durable; do not continue activation after a recovery error. The HTTP socket is root-owned 0600; the gateway runs as haven-wishlist-web with AF_UNIX only and no private database or model/Telegram credentials.

The initial rollout does not alter Serve automatically. Inspect the existing configuration and verify the local HTTP socket and owner denials before adding exactly this route (Tailscale 1.104.5 was inspected on the pilot; 1.104.4 source documents Unix proxying):

sudo tailscale serve status --json
sudo tailscale serve --bg --https=443 --set-path=/wishlist unix:/run/haven-wishlist-http.sock
sudo tailscale serve status --json

Preserve the dashboard /, private docs listener, SSH and tailnet policy. Refuse a conflicting pre-existing /wishlist handler. Keep Funnel absent. Verify real HTTPS access from an authorized device and the gateway/collector account’s denial at the HTTP socket. Before handoff, take and exactly reconstruct a new encrypted backup containing schema 6, refresh observability, verify healthy resume state and compare deployed hashes against the checked source. Test failures and owner acceptance remain explicit; a successful service start is insufficient.

To withdraw only this new route, remove /wishlist with tailscale serve --https=443 --set-path=/wishlist off and stop its HTTP socket/service. Keep the database and compatible domain/recovery code. File snapshots are not a database rollback and must not be used to install old code over schema 6.

The identity-header and Unix-socket contracts were checked against the Tailscale Serve guide, installed CLI help and pinned Serve source. Waitress socket activation and bounded server settings follow its official activation guide and server arguments.

Unix proxy compatibility: Serve 1.104.5 rewrites the backend Host to localhost and replaces X-Forwarded-Host/X-Forwarded-Proto with the outer request. Waitress trusts those two headers from its Unix localhost peer because the inherited HTTP socket admits root exclusively; the application then checks the resulting exact owner authority and Origin. The proxy setting must never be reused with an unprotected listener. Production asset and API URLs use the absolute /wishlist/ mount so opening /wishlist without a trailing slash still works.

The following paragraphs document the retained calculation/data contract and the earlier delivery, not an enabled statistics screen.

Retained contract and earlier delivery

The web now implements the owner-confirmed spending and net-savings summaries, globally and for each category. This is checked source and synthetic acceptance, separate from pilot installation and owner acceptance. The initial category order is retained. No collector, model or shop request is needed to calculate a summary.

The period control defaults to the current Prague calendar month and offers month, year and all history. Arrows navigate earlier months/years; future navigation is disabled. Purchases are selected by their saved purchase date; legacy timestamps without a saved date are converted to the owner’s configured time zone. Corrections move a purchase into its corrected period; voided purchases contribute nothing. Existing version/lifecycle protections still prevent cancellation from overwriting newer changes. Metadata-only edits do not prevent cancellation.

Summaries follow the list’s search and shop, stock, mode and lifecycle filters. In the default active view, purchased one-time items are excluded; select Purchased or All non-removed to include them. Removed items are included only through the Removed filter. Category filtering and category totals use the saved purchase category, while the list groups by the item’s current category. A moved item can therefore contribute historical purchases to its former category without appearing in that category’s current list. The UI explains this distinction in expandable help.

Migration 7 appends a constrained purchase category and an owner/entry index without changing existing purchase values or history. All pre-migration purchases use uncategorized; the current item category is never used to guess their original category. New web and web-enabled Telegram purchases capture the category at recording; amount, quantity and date corrections keep that saved category. A backdated new purchase uses the item’s category at recording; the service cannot infer an undocumented past assignment.

Spending uses paid unit price times quantity. Net savings use the already saved reference mean; overpayment reduces savings. Purchases without paid prices are excluded from both monetary totals and counted explicitly. Known paid amounts without a reference contribute to spending and an explicit unknown-savings count. A wholly unknown sum displays a dash; a selection with no purchases displays zero. Partial known sums remain visible with the missing-data counts. Category subtotals apply the same rules. Later observed prices cannot rewrite saved references.

web.statistics is an owner-authenticated read through the existing gateway/domain boundary. Arguments are period (month, year, all), date (an ISO calendar date in the selected period, no later than today) and an optional filters object with state, category, shop, stock, mode and search. Category values are the existing domain codes; blank values mean no restriction. State defaults to default; supported alternatives are purchased, removed and all. Unknown fields/types are rejected. The response returns total and categories, each with count, unknown_price, unknown_reference, spending and savings. Monetary totals are exact integer-halere decimal strings or null, retaining precision beyond JavaScript’s safe integer range.

One read transaction produces the entire summary independently of paginated item details. The read refuses more than 10,000 purchased item identities or 128,000 non-voided purchases instead of presenting a truncated total. It writes no receipts or events. The browser clears old totals while loading, ignores superseded responses and shows an explicit unavailable state with retry on failure. Both the observability exporter and backup compatibility checks support schema 7. Deploy compatible domain, gateway, UI, observability and recovery helpers together using the existing guarded web playbook and fresh verified backups. Schema-6 code must not reopen the migrated database; application file rollback cannot remove the category column or rewind purchase history.

Verification

The maintained domain and JavaScript suites cover historical categories, unknown prices/references, signed net savings, exact large amounts, period boundaries, corrections, voids, identity/filter validation and bounded reads. Migration tests retain all schema-6 purchase fields and refuse an old reader. Backup/recovery tests preserve the new category together with amount, quantity and reference.

An opt-in browser acceptance uses the existing hash-pinned probe dependencies, a temporary SQLite database, local self-signed HTTPS and a fresh sandboxed Chromium profile. HTTPS certificate bypass is confined to this synthetic loopback fixture. It uses the production UI/gateway and in-process domain transport; the normal socket tests independently cover UID admission. It never connects to the pilot, a shop, an existing browser profile or a model. Run from the public repository with the separate probe environment:

/absolute/path/to/probe-env/bin/python -m research.wishlist.statistics_browser \
  --chromium /absolute/path/to/chromium \
  --output build/statistics-qa

The current fixture checks that the summary section is absent and no automatic aggregate request is made, while desktop/mobile lists, filters, detail, price history and purchase recording still work. It writes synthetic screenshots and a small result receipt to the chosen output directory. These checks do not establish live migration, installed service isolation or owner acceptance.

Product overview, detail and intake

The current home page uses responsive product rows. It groups by category and displays the shop, current or last known price, availability and meaningful changes. Search, category and sort are exposed alongside the list. Shop, availability, purchase mode and lifecycle are under additional filters. Removed and purchased views remain accessible. The product name, price and change are read together on wide and narrow screens. The shop and purchase action remain independently reachable. A fixed-size fallback keeps each product in place while its photo loads.

The initial list and a manual retry show placeholder rows while all pages of list data and the photos in the visible viewport load. The rows and their ready photos appear together. Missing or failed photos fall back to an icon. Photos farther down or still pending after five seconds use fixed-size placeholders while they load. The list and product preview share the same placeholder styling and respect reduced motion. A failed list request offers a retry. A periodic refresh keeps the existing rows in place while it fetches the next result.

The compact activity strip uses a rolling seven-day window and the latest verified transition per product and signal. Price changes compare adjacent observations of the same offer. An identical subsequent price does not erase a recent transition. Failed collection and unavailable offers do not advertise stale prices as fresh changes. A label about no detected changes is scoped to the available evidence. A first observation is not a price change.

web.list and web.get expose the optional latest price change (stats90.price_change, signed integer haléře and observation timestamp) and the latest verified stock change (stock_change, previous availability and timestamp). Existing fields and commands retain their meanings. The collector retains the new availability detail alongside the latest verified state in the existing metadata record, including successful checks without a price. Equal follow-up checks preserve the transition. No migration is needed; older stock events are not inferred. Price checks and collection limits are unchanged.

The detail is a desktop drawer and a full-height mobile dialog. It prioritizes the shop link and current price. The price chart appears when daily averages differ; a single measurement or flat daily averages get a text summary. The measured-days table, observation count, dates without a price in the actual tracking interval and last successful check remain visible. Comparison statistics give their own measured coverage, separately from the selected chart period.

Adding an item starts with its HTTPS URL. Name, category, mode and note can be provided up front or edited after saving. The saved item opens in its detail with collection status. Existing bounded collection resolves a name, availability and price when it can. See the preview and category flow below. The form starts a new purchase with an empty price and offers a separate action to use the last observed amount. Corrections open with the saved price. Validation identifies the affected field, and voiding a purchase requires confirmation. Clicking outside a changed form leaves it open. Escape and the close controls ask before discarding the changes.

The two optional owner-supplied webfonts are served from the existing authenticated origin. Obtain original WOFF2 copies for your own installation from Gambarino and General Sans under the foundry’s license. Supply an absolute local directory via haven_wishlist_web_fonts to the existing web playbook. It accepts only the files named gambarino.woff2 (regular) and general-sans.woff2 (normal variable weight). No font binaries are bundled in the source repository. Without optional assets the stylesheet uses local/system fonts. Browser clients do not connect to Fontshare.

The local HTTPS acceptance above also checks eight viewport widths from 320 to 3840 pixels, keyboard focus during refresh and detail loading, actual price/availability transitions, single and changing price histories, URL-only intake, and purchase correction, cancellation and removal undo. Pass --fonts /absolute/path/to/owner-fonts to exercise the optional files. Existing data and automatic collection remain the sources of truth.

The interface uses green accents and warm neutral surfaces, with a wider reading area on large displays. The serif stays with the brand and the sans serif serves product details and controls. Selects retain native keyboard and assistive-technology behavior. Browsers that support customizable selects render the palette-matched picker. Text fields and selects use the same focus treatment. Filters, additional fields and dialogs animate when the browser supports the transition and the reader allows motion.

Optional product preview before saving

On the web, a complete HTTPS URL starts a preview after a short delay. The preview shows the product name, shop, public CZK price and availability when the adapter can verify them. An out-of-stock result can include a name and availability without a price. The user can edit the suggested name or skip the preview and save the link manually. Changing or closing the form cancels the browser request and discards superseded results. Saving uses the existing explicit web.add command and starts the regular collection workflow. The preview itself never creates an item, a job or an observation.

The gateway routes authenticated, CSRF-protected web.preview requests to a separate peer-authenticated service over a Unix socket. It accepts only an HTTPS URL and uses the same bounded, allowlisted fetch process and exact-offer extraction as regular collection. The service has a separate user and no access to the domain socket, database or credentials. The gateway permits two simultaneous product preview requests. The worker admits at most one product fetch per supported shop and bounds it to eight seconds. It respects a shop’s preview Retry-After in memory and postpones previewing for at least a day after HTTP 429. This preview cooldown is independent of the scheduled collector. The Alza preview is unavailable. A gateway configuration without a preview endpoint retains manual intake.

The wishlist web playbook installs the worker, its root-owned code, and the gateway endpoint config under the existing maintenance lock. Take the documented fresh verified backup before running the playbook. A pre-upgrade snapshot covers the added unit and the modified code and config. To roll back across the introduction of preview, stop and disable the preview unit before restoring or removing its files. The preview has no independent state to back up.

The add dialog starts with the URL field. Saving and optional fields become available after the preview finishes or the owner explicitly skips it. For a plain Fabini product URL, the preview can fill in the exact variant URL when the canonical product data identifies a single verified variant. The editor shows the completed URL and uses it for saving. With multiple variants, paste an explicit variant URL. Regular collection still verifies the exact saved offer. Long merchant titles are shortened for the editable name suggestion. Existing names are kept as entered.

A Czech Intimissimi URL with a colour parameter can offer a size picker when the primary product DOM and structured SKUs agree on the model and colour. The selected size opens a separate exact-variant preview. Price, availability and photos come from that verified variant. A colour page by itself provides only size choices.

An eligible product preview returns a short-lived category token. The browser keeps one skeleton visible until product data, the category suggestion and the bounded photo load settle, then shows the preview and enables saving together. The preview worker exchanges the one-use token for the verified product title and requests a category through the language socket restricted to its UID. The request contains only the public merchant title. The model receives the fixed category codes in a short instruction and returns one code. The request uses GPT-6.1 Terra with reasoning disabled, no tools and no repeated provider attempt. It prefers the latest explicit OAuth enrollment labeled wishlist on the pinned Codex origin. A rate limit and a short deadline bound the call. If a suggestion is unavailable, the editor indicates that outcome and offers the default or a manual category. The owner can override any suggestion before saving. This path has no write access and does not export traces.

Product photos

The exact-offer extractor can record an image URL from the same variant-specific Product record as its verified offer. Ambiguous, missing or unapproved candidates leave a placeholder. An accepted collection records the URL alongside the existing verified availability in the same transaction. Older entries acquire it on a subsequent successful collection, with no schema migration or history rewrite.

For iFantazie, the verified Product record can also refer to the shop’s own image directory on the shared Shoptet CDN. Intimissimi prefers a bounded image from the primary gallery whose filename matches the verified model and colour. Images already saved with a recognized original Intimissimi catalog URL use the merchant’s 600-pixel rendering of the same file.

List, detail and preview return only authenticated same-origin image paths. The gateway resolves each path against either a saved offer or a short-lived preview record. The preview service fetches the approved merchant asset via the existing checked HTTPS transport, denies redirects and restricts it to JPEG, PNG and WebP with a byte and dimension limit. The browser receives a placeholder if the request fails. Image requests have separate concurrency limits and use a bounded in-memory cache. No shop request is made by the browser and the preview unit still has no database access.

Kitchen and clothing categories

Kuchyně (kitchen) and Oblečení (clothing) are available in the category picker, filters and automatic suggestions. The order and values of existing categories are preserved. Existing items are reclassified only when the owner chooses another category, and purchases keep the category recorded at the time of purchase.

Migration 8 expands the allowed values on the item and purchase category columns in one transaction. Keep schema-8-compatible recovery code and verify a new backup after rollout.
