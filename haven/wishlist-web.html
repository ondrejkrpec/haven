Wishlist web: first interaction preview

Historical first delivery, 2026-11-18: a local, responsive interaction preview implemented the confirmed owner flows using synthetic data. That standalone preview is not connected to the pilot, its database, Telegram, shop fetchers or model credentials. The production implementation follows below; deployment and live acceptance must be recorded separately. Spending/savings dashboard requirements are deliberately unfinished; the UI labels that area as pending rather than displaying invented totals.

Run and review

Use the existing local Python environment and Node.js versions documented in local development. No new dependencies or build step are required:

.venv/bin/python -m scripts.wishlist_web_preview --port 8765

Open http://127.0.0.1:8765/. The preview serves only six explicitly allowed UI files from web/wishlist, binds IPv4 loopback, checks the Host header, refuses symlinks and sends a restrictive Content Security Policy. It does not serve a checkout, directory listing, neighboring private files or a general HTTP API. This development server must not be exposed as a production service.

Data stays in the current browser’s local storage under a versioned preview key. All seeded names, shops and prices are synthetic; shop links use reserved example domains. Added URLs are saved locally without fetching them. No telemetry, remote fonts, image downloads or external scripts run. The preview reset is reversible within the current session. Storage failures are visible; the browser is not a production backup or authority boundary.

Implemented interactions

  • Category groups, descending percentage/absolute price advantage within groups, name search and shop/category/availability/purchase-mode/lifecycle filters.

  • Default active view includes unavailable items and recurring items with muted notifications. Purchased one-time and removed entries have explicit filter views.

  • Desktop table and compact mobile rows; a modal side panel becomes full-screen on mobile. Keyboard focus, modal escape/close, field labels and live announcements support normal keyboard use.

  • Detail with immutable shop link, availability, successful-check/addition dates, editable name/category/mode/note, and month/90-day/year/all-history chart. The chart defaults to 90 days and offers an underlying daily-price table. Missing dates are gaps, not fabricated prices. Optional product images are not included in this version.

  • Purchase form uses a per-unit price, integer quantity and editable purchase date, showing the total before confirmation. Item detail lists purchases with correction and cancellation. Stale lifecycle cancellation is refused rather than overwriting a newer state.

  • One-time purchase leaves the active view. A recurring purchase mutes notifications for approximately 30 days, keeps its entry active and preserves price history. The remaining-days icon can restore notifications immediately. No actual notifications or collector run in this preview.

  • Removal is immediate and reversible through an undo notice or removed-items filter. Restoring a purchased entry does not reopen it.

  • Collection failure retains an explicitly dated last known price and labels its comparison. Verified unavailability without price hides the current price/comparison but preserves historical data.

  • The manual price-check control explicitly reports that live collection is not connected. It never invents a price or reports a successful fetch.

Price and purchase calculations

Money uses integer halere. For the inclusive 90-day Prague calendar window, average all valid prices within each measured day, then equally weight those daily means. Missing days contribute no value; the first real price immediately establishes both average and minimum. Minimum uses the lowest individual price observed in the window. Displayed reference means round to a haler.

Capture the reference mean available at the purchase date. Historical purchases exclude later calendar days, including across Prague DST changes. Savings per purchase are (reference mean - paid unit price) * quantity; overpayment is negative. Later observations cannot rewrite the saved reference. Amount/quantity corrections preserve that reference; changing the date recomputes it from that date’s available history. Purchases without any known reference remain explicitly unknown, not zero savings.

The standalone preview model does not change existing domain behavior: the pilot still uses its original classification and pause/collection semantics. Unifying those behaviors requires a separately tested domain change before production integration. Local lifecycle revision checks are interaction guards, not server authorization or distributed concurrency control. Concurrent browser tabs receive a change warning; they are not a synchronized database.

Validation and remaining scope

node tests/wishlist_web.test.mjs
.venv/bin/python -m unittest tests.test_wishlist_web -v

The model tests cover first-price averages, daily weighting and gaps, money precision, stock/failure distinctions, purchase references and backdating, DST boundaries, notification-only muting, correction/cancellation and reversible removal. HTTP tests cover the asset allowlist, response headers, Host denial and symlink refusal. Browser acceptance should exercise desktop/mobile flows and storage reloads; synthetic checks do not establish production authentication or live shop behavior.

Before production work, finish dashboard statistics (filter scope, historical purchase categories and past-period controls), review the first UI, settle access/write authentication and the URL under the existing private Haven origin, and define service boundaries, migrations, retry/idempotency and acceptance. Keep the existing domain as the sole production writer. Do not expose its ingress socket or reuse Telegram identity claims from a browser. Wishlist integration and Nora wording must share the resulting domain contract. Alza remains the final separate wishlist item; the final Haven security/architecture audit still follows the completed wishlist.

Production integration, 2026-11-18

The production adapter adds scripts/wishlist_web_domain.py, a dedicated peer-authenticated endpoint in the existing domain process, and scripts/wishlist_web_gateway.py, a network-isolated HTTP adapter. ADR 0019 records authentication and isolation. These implementation and synthetic results are distinct from live pilot acceptance.

The production page uses same-origin requests at /wishlist/api/command; it never reads demonstration local storage, falls back to sample products, or writes a second database. Reads are bounded and paginated. Mutation request IDs survive uncertain responses and re-bootstrap; the domain commits changes, events and receipts atomically, with version conflicts and signed owner-bound cursors. Tests include discarding the HTTP response after a committed recurring purchase, then retrying the same request ID without creating a second purchase.

Price means use equally weighted Prague calendar days, including the first observation. Persisted purchase references remain fixed when later prices arrive. Original purchase rows without a paid amount stay unknown; cancellation cannot guess an undocumented prior lifecycle. Legacy purpose/recipient fields remain as history but no longer block new intake. Recurring purchases mute notifications for approximately 30 days while daily collection continues. A manual refresh respects host backoff and a ten-minute per-offer minimum; the dedicated path unit wakes the existing bounded collector, with the timer as fallback. No offer notifications or cross-shop recommendations are added by this integration.

Prepare and install

Build an independent dependency artifact; do not replace the JSON Schema or native Hermes environments:

.venv/bin/python -m scripts.wishlist_dependencies build \
  --directory /absolute/path/to/http-artifact --requirements requirements-web.txt
.venv/bin/python -m scripts.wishlist_dependencies bundle \
  --directory /absolute/path/to/http-artifact --requirements requirements-web.txt

Take and verify a fresh backup with the existing controller. Then use the explicit private inventory and private owner configuration:

ANSIBLE_CONFIG=ops/ansible.cfg ANSIBLE_HOME=build/ansible \
  .venv/bin/ansible-playbook -i /absolute/path/to/private/ops/inventory.yml \
  ops/wishlist-web.yml -e haven_wishlist_web_authorized=true \
  -e @/absolute/path/to/private/ops/wishlist-web.yml \
  -e haven_wishlist_web_dependencies=/absolute/path/to/http-artifact

The private variables name haven_wishlist_web_origin (the existing HTTPS origin) and haven_wishlist_web_owner_login (the exact owner Tailscale login). The playbook installs and resumes services under shared maintenance exclusion, checks that the last backup is accepted and under two hours old, snapshots only declared code/configuration files, installs compatible backup helpers first and arms durable resume journal version 3 for the collector timer and three existing writers. Recovery runs while the same lease is held, then releases the lease even on failure. Failed resume intent remains durable; do not continue activation after a recovery error. The HTTP socket is root-owned 0600; the gateway runs as haven-wishlist-web with AF_UNIX only and no private database or model/Telegram credentials.

The initial rollout does not alter Serve automatically. Inspect the existing configuration and verify the local HTTP socket and owner denials before adding exactly this route (Tailscale 1.104.5 was inspected on the pilot; 1.104.4 source documents Unix proxying):

sudo tailscale serve status --json
sudo tailscale serve --bg --https=443 --set-path=/wishlist unix:/run/haven-wishlist-http.sock
sudo tailscale serve status --json

Preserve the dashboard /, private docs listener, SSH and tailnet policy. Refuse a conflicting pre-existing /wishlist handler. Keep Funnel absent. Verify real HTTPS access from an authorized device and the gateway/collector account’s denial at the HTTP socket. Before handoff, take and exactly reconstruct a new encrypted backup containing schema 6, refresh observability, verify healthy resume state and compare deployed hashes against the checked source. Test failures and owner acceptance remain explicit; a successful service start is insufficient.

To withdraw only this new route, remove /wishlist with tailscale serve --https=443 --set-path=/wishlist off and stop its HTTP socket/service. Keep the database and compatible domain/recovery code. File snapshots are not a database rollback and must not be used to install old code over schema 6.

The identity-header and Unix-socket contracts were checked against the Tailscale Serve guide, installed CLI help and pinned Serve source. Waitress socket activation and bounded server settings follow its official activation guide and server arguments.

Unix proxy compatibility: Serve 1.104.5 rewrites the backend Host to localhost and replaces X-Forwarded-Host/X-Forwarded-Proto with the outer request. Waitress trusts those two headers from its Unix localhost peer because the inherited HTTP socket admits root exclusively; the application then checks the resulting exact owner authority and Origin. The proxy setting must never be reused with an unprotected listener. Production asset and API URLs use the absolute /wishlist/ mount so opening /wishlist without a trailing slash still works.
