Alza: isolated Chromium on a virtual display

Status, 2026-11-13: the pinned browser is installed separately on the Ubuntu pilot. Installed UID/file restrictions, private networking, sandboxed Chromium startup and normal descendant cleanup passed. Its normal VPS egress still returns Cloudflare verification. Two fresh-context reads using the exact installed renderer on that VPS succeeded through a temporary restricted workstation egress relay. Permanent egress and production collection acceptance remain open; the relay was removed after the experiment.

This implements the path demonstrated by the historical headed/Xvfb experiment. The optional browser endpoint provides a second source path; it does not guarantee access from every network. There is no CAPTCHA interaction, stealth plugin, modified browser identity, account login or reuse of the owner’s browser/session.

Data flow and trust

haven-collector still obtains jobs from the sole domain writer. For adapter alza-public-price-v1, its explicit optional browser endpoint selects haven-wishlist-browser.service; other shops retain the bounded direct fetch worker. The browser authenticates the collector UID before reading the strict JSON frame; the collector verifies the browser service UID before sending. Every browser request binds the exact Alza URL and job digest. Domain completion still rechecks job/attempt, generation, entry version, lease and owner-scoped offer.

The separate haven-browser identity has no wishlist/Telegram/model/backup data access or domain socket group. The systemd unit uses PrivateNetwork=yes: its only IP listener is its own loopback proxy, and it has no direct Internet route. That proxy authenticates haven-egress over a separately permissioned Unix socket. The egress service accepts only the browser UID and HTTPS CONNECT to a fixed set of Alza hosts. It resolves all answers, rejects nonpublic/special destinations, connects the checked numeric sockaddr and relays browser TLS unchanged. Chromium retains its original-host SNI and certificate verification.

The browser allows only GET/HEAD requests to www.alza.cz, cdn.alza.cz, image.alza.cz, webapi.alza.cz and c.alza.cz; main-frame navigation must retain the requested exact product identity. Service workers, WebSockets and downloads are disabled. The broker independently checks destination and port, so route hooks are not the network boundary. The network namespace and separate UID/cgroup are deployment requirements; the same-UID workstation integration establishes wiring, not production OS isolation.

Lifetime and resource bounds

One browser job runs at a time. Each job creates a new nonpersistent Chromium context, a temporary home/cache and an Xvfb display with a private MIT-MAGIC-COOKIE-1 file. Xvfb has no TCP listener. Browsers, display authorization and temporary data are closed/removed after the job; nothing is added to application backups or reused as login state.

The renderer has a 60-second internal budget, a 65-second external process budget, a 70-second collector IPC deadline and the existing 120-second domain lease. The daemon admits at most two IPC connections. The egress broker admits at most eight concurrent tunnels, limits a tunnel to 16 MiB and 75 seconds, and limits each 75-second window to 64 connections/64 MiB. HTML extraction retains the 4 MiB bound. The systemd browser limit is 1536 MiB/256 tasks/one CPU; the broker limit is 128 MiB/48 tasks/one-quarter CPU. These configured bounds are not measurements of pilot headroom.

Chromium may detach child process groups. Cleanup therefore tracks descendants by PID/start time and, in production, sweeps only the exact haven-wishlist-browser.service cgroup after a worker ends. It never sweeps a shared developer/user cgroup or another service. Production daemon startup requires that exact managed cgroup; normal execution retains chromium_sandbox=True and never adds --no-sandbox. Service shutdown additionally kills the complete cgroup.

The private-network browser unit and public-network broker run independently of the existing wishlist writer and interpreter. A lost browser reply cannot write SQLite: only the collector’s still-current domain completion can do that. Failure remains bounded and the expired lease is reconciled by the existing scheduler. The collector’s service budget allows up to twenty sequential browser jobs; timers do not start parallel copies of the same oneshot unit.

Public price validation

alza-public-price-v1 requires an exact JSON-LD Product/Offer, SKU, CZK, recognized availability and explicit NewCondition. Member/quantity offers, conflicting offers and unknown query/variant changes are refused. The primary DOM price box must be unique and explicitly use the observed public ads-pb—​basic layout; member/code/login/instalment labels are refused.

The accepted amount is the public gross price shown in that primary box, excluding strike-through and VAT-exclusive prices. Decimal displays must match metadata exactly. A whole-crown display must equal half-up rounding of the structured amount. This handles the observed fractional-metadata/whole-crown-display difference without silently using a cheaper metadata figure. Unrecognized or inconsistent layouts remain failures. Checkout, coupon, shipping and future-layout guarantees are still absent; observations retain conditions_verification=not_verified.

Direct Alza HTML, if accessible, uses the same public-price validator. When no browser endpoint is selected, direct access can still return 403. The earlier JSON-LD-only adapter is superseded; old completed receipts/history remain intact, while an outstanding old-version job cannot admit a new-version result.

Explicit preparation

The runtime pin fixes Playwright 1.64.1 and Linux x86_64 Chromium 156.0.8078.4/revision 1248 with a SHA-256 for the complete official archive. The downloaded archive was compared against all 301 cached browser files used by the successful experiment. Other architectures need a separate reviewed pin. The optional dependency lock is separate from coordinator/public-check dependencies.

ops/wishlist-browser.yml requires an explicit private inventory, haven_browser_install_authorized: true and a local haven_browser_chromium_archive matching that digest. It creates independent non-login accounts, builds a separate hash-pinned environment under an unprivileged build account, freezes /opt/haven-wishlist-browser as root-owned files and installs only the declared public modules. It neither overwrites the active domain runtime nor starts/enables the browser units.

Preparation refuses running browser services and incompatible in-place runtime/dependency replacements. An apt simulation refuses planned existing-package upgrades/removals; the install uses the current package indexes, --no-upgrade and --no-remove. It does not refresh repositories or authorize general OS maintenance. The declared packages and repeat preparation passed on the Ubuntu pilot without existing-package upgrades or removals.

Ubuntu’s user-namespace restriction remains enabled. The staged AppArmor profile grants user-namespace admission only to the new root-owned Chromium executable so Chromium can create its renderer sandbox; it does not disable global AppArmor/namespace policy or change existing profiles. The scoped profile parsed and sandboxed Chromium started on the target while the global user-namespace restriction remained enabled.

After preparation and authorized activation, configure the collector endpoint explicitly:

{
  "socket": "/run/haven-wishlist-collection/request.sock",
  "service_uid": 2401,
  "browser": {
    "socket": "/run/haven-wishlist-browser/request.sock",
    "service_uid": 2405
  }
}

IDs are synthetic. The domain UID and browser UID must be distinct. The W4 preparation renderer supports haven_wishlist_browser_enabled: true after the browser identity/group exists; otherwise it emits no browser endpoint. W3 activation still requires its schema-5-compatible backup/migration acceptance. Browser preparation alone does not activate daily collection or change Nora’s independent native guard.

Before pilot acceptance, verify actual UID/group denial, private network namespace, denied private destinations, scoped AppArmor sandbox startup, timeout/descendant cleanup and memory alongside the current services/backups. Start only the two browser-related units, perform one bounded read under the collector identity, then verify the complete current domain/Telegram path and repeated collection. Preserve the distinction between a successful source read and day-spaced operational stability.

Verification and evidence

The synthetic suite is .venv/bin/python -m unittest tests.test_wishlist_browser tests.test_wishlist_fetch tests.test_wishlist_collection tests.test_wishlist_operations -v. It exercises public-price disagreement, member/used/variant rejection, peer credentials before DNS, pinned proxy forwarding to a temporary test server, transfer limits, worker cancellation, PID reuse/cgroup exclusion and systemd unit parsing. It never installs Playwright, opens a shop, uses credentials or contacts a model.

The local integration receipt records exact source hashes, browser/archive identity, direct and integrated outcomes, historical fixture errors and limits. Raw DOM, screenshots, actual product details and temporary SQLite files stay outside public Git/build inputs. No successful local run establishes installed production identities or network namespaces.

The retained opt-in roundtrip runner takes an explicit local executable configuration, one reviewed Alza target JSON and a new short private work directory outside the repository. It deliberately uses same-UID temporary services, never production accounts. Under the separately pinned browser Python, run:

timeout 90 "$WISHLIST_BROWSER_PYTHON" research/w3/browser_roundtrip.py \
  --config "$WISHLIST_BROWSER_CONFIG" --target "$WISHLIST_BROWSER_TARGET" \
  --work "$WISHLIST_BROWSER_WORK"

The target is exactly {"url":"REVIEWED_HTTPS_PRODUCT_URL"}. The runner retains private result/SQLite files only in that fresh work directory and reports accepted-observation and immediate-repeat counts. Public checks never invoke it against a shop. It is not a way to bypass the production daemon’s cgroup/identity requirements.

Context7 resolved Playwright 1.64.1 but did not return the needed API sections; the implementation used the exact installed API and official launch reference, network interception and non-root sandbox guidance. Browser contexts separate cookies; OS identities, network namespaces and process groups provide the other boundaries.

Context7 had no ansible-core 2.21.5 version; preparation also uses the official 2.21 user, archive and argv references, including explicit group append semantics. Local syntax/lint acceptance does not establish target package or AppArmor availability.

Installed browser result, 2026-11-11

Preparation passed with the exact archive/dependency pins and left the existing domain runtime independent. Actual browser/egress processes had distinct non-login UIDs, no effective capabilities and NoNewPrivileges. Checks inside their installed mount/network namespaces denied coordinator, wishlist, interpreter and backup private files. The browser’s namespace had no direct Internet route; the broker retained networking. A bounded request from the collector UID reached Alza through those units. After normal completion the browser cgroup returned to its single daemon task, with no remaining Chromium/Xvfb descendants. The observed browser cgroup peak was approximately 745 MiB; this sample does not establish worst-case simultaneous capacity or forced-timeout acceptance.

The installed source request returned HTTP 403. Disposable diagnostics identified blocked Cloudflare resources in the intentionally small allowlist. A separate test broker allowed the exact challenge origin and narrowly scoped verification POSTs, and the page then displayed a visitor-verification widget. A separately launched ordinary Chromium attached through CDP, including one click on the visually reviewed verification checkbox, still produced no product price. These diagnostics were not adopted as the production adapter; they prove neither automatic challenge completion nor functional Alza. No account or personal browser profile was used.

The existing adapter continues to fail visibly rather than inventing a price. A working source path from a suitable execution environment is still required before accepting Alza. Installing browser packages or passing workstation extraction is insufficient evidence for the VPS. Diagnostic units and temporary data are removed after inspection; no general OS update, firewall or Tailscale change is part of this work.

Context7 resolved Playwright 1.64.1 but did not provide the requested CDP details; the diagnostic used the official CDP API. Cloudflare documents network/challenge failures and unsupported automated challenge environments. These references explain limitations, not a guarantee that another network will be admitted.

Egress comparison, 2026-11-13

Source baseline: 45eb0086961bcb330b80266dfbf1d00affa75094. SHA-256 comparison matched the installed browser, egress and price-validation modules to that revision. The existing browser service returned HTTP 403 for the reviewed product. DNS returned only IPv4 addresses; the host’s available IPv6 route therefore provided no alternative source path.

Two separate disposable diagnostics allowed the observed Cloudflare origins and verification POSTs, then added the observed hagen.challenges.cloudflare.com dependency. Required verification resources loaded, but the product remained behind the visitor-verification page with no price box. Neither temporary allowlist was adopted in production.

A further comparison kept sandboxed Chromium/Xvfb on the VPS and moved only its bounded HTTPS egress to the workstation through an SSH Unix-socket reverse forward. The workstation broker admitted only the local SSH UID and the declared public destinations. TLS remained end to end between Chromium and Alza. The disposable browser unit retained its private network, dedicated browser UID, private-data exclusions and resource limits. No workstation browser profile, site login or saved cookies were used.

The diagnostic renderer returned HTTP 200 and a validated public offer. Two subsequent reads invoked the exact installed scripts.wishlist_browser.render with the original request policy and the original five-host broker allowlist. Both fresh profiles independently returned HTTP 200 and the same accepted public offer. The comparison demonstrates a working source-read path from the VPS through that network; it does not identify Cloudflare’s decision rule or establish the future reliability of the workstation connection.

The sanitized comparison receipt records scope, module hashes and outcomes. Private drivers and detailed results remain in the instance repository. Temporary systemd units, Unix sockets and the SSH tunnel were stopped and removed. Production configuration and wishlist data remained unchanged, with no model calls or Telegram sends.

This comparison is not an activation plan. The diagnostic used the existing administrator connection only for a bounded experiment; it is not an unattended deployment recipe. A deployment requiring VPS-only operation still needs a working source path through that VPS network. An installation choosing an external relay would instead need an available egress host, a separately restricted identity, authenticated transport and service lifecycle; a workstation relay would defer collection whenever that machine sleeps, disconnects or stops running. The complete domain/collector/Telegram path, failure/reconnect, restart, measured capacity and another daily cycle remain unaccepted.

Context7 resolved the pinned Playwright version but returned no matching routing documentation. This investigation used the official routing reference and navigation reference, alongside the Cloudflare references above.

VPS-only follow-up

The comparison was followed by bounded attempts without workstation egress. Normal anonymous requests to the public, mobile and API origins returned HTTP 403. Two observed read-only product API routes also returned 403; the router route remained blocked on both public/API origins with the mobile client’s expected non-secret headers. No account token or login was used.

A separate hash-locked curl_cffi==0.16.1 experiment used its chrome150 profile, verified TLS, checked public destination addresses, manually validated redirects and a 4 MiB response limit. The product and router API returned 403. That research dependency was removed from the VPS and was not added to application requirements.

An official stable Chrome 157.0.8103.78 Debian package was verified against Google’s package-index SHA-256 and extracted into a separate temporary root. No package installation or existing-browser replacement occurred. A temporary executable-specific AppArmor user-namespace admission preserved the global restriction. Ordinary sandboxed Chrome attached through CDP remained on HTTP 403, both without interaction and after one visually reviewed verification-checkbox click. Earlier fixture failures stopped before navigation because the extracted parent directories were not traversable by the dedicated browser UID; they are recorded separately from these completed source checks. The profile, extracted browser and disposable units were removed.

Finally, an explicit public CDN IPv6 connection completed TLS for the original Alza hostname despite the missing Alza AAAA record. Both the unchanged renderer and a separate ordinary-browser control through that IPv6 path remained blocked. The latter removed application request-routing hooks while retaining the peer-authenticated, destination-bounded broker, and still obtained no product after the reviewed checkbox click. This was a diagnostic address override, not a production resolver change. Cloudflare’s IPv6 documentation describes DNS advertisement separately from transport; it does not establish support or reliability for this override.

These negative results narrow the remaining work to a usable source-access path. They do not establish that all possible VPS-only clients fail, nor that a different proxy or address would succeed. The production Alza adapter remains unaccepted, and no external service was enrolled during these experiments.
