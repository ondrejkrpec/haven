H1.3: Private administration with Tailscale

Status on 2026-10-28: private administration is verified. The VPS, computer and phone are enrolled; restricted policy and tag:haven permit key-based OpenSSH over private IPv4/IPv6. Public SSH allowances were removed for both address families, a fresh public IPv4 connection timed out, and private connections passed. The owner confirmed console login and phone connectivity over mobile data. The narrow fallback was exercised before reapplying the final configuration. A subsequent controlled restart verified automatic return of private access; public IPv6 could not be tested from the inspection computer.

Intended result

Keep OpenSSH, the ubuntu administrator and existing key authentication. Tailscale provides the private network; Tailscale SSH is a different login mechanism and is not required for this rollout. The phone’s Tailscale app provides connectivity; an SSH client with a separately managed key would additionally be needed for terminal administration from that phone. Later dashboards can use a browser over the tailnet after their own access rules are added.

Use the owner’s personal account with protected sign-in and independent recovery material. Tailscale’s current Personal plan is free for non-commercial personal use; verify eligibility and limits when enrolling. Keep login URLs, auth/API keys, node state, account identities and actual tailnet addresses outside public sources. Never give the runtime haven account or coding executors the administrator’s SSH identity.

Inputs and owner actions

  • Create the personal Tailscale account and finish interactive identity-provider authentication. The operator cannot complete the owner’s login or MFA on their behalf.

  • Enroll the administration computer and phone into that same tailnet. On iOS, the owner installs the official app and approves its VPN configuration.

  • Verify provider-console login, account recovery and a way to regain administration if the sole computer/key is lost before closing public SSH.

  • Confirm the actual account identity and review the complete tailnet policy. Do not replace an existing network’s policy without reviewing its other devices and required access.

Staged installation

The official stable package page has an Ubuntu 26.04 resolute repository. The executed installation used its dedicated signed keyring and source list. Only this repository’s metadata was refreshed, followed by a simulation and installation of the exact candidate:

sudo apt-get update \
  -o Dir::Etc::sourcelist=/etc/apt/sources.list.d/tailscale.list \
  -o Dir::Etc::sourceparts=- -o APT::Get::List-Cleanup=0
sudo apt-get -s install --no-install-recommends tailscale
sudo apt-get install --yes --no-install-recommends --no-upgrade tailscale=1.104.4
sudo systemctl enable --now tailscaled.service
tailscale version

The simulation and actual transaction both reported one new package, zero upgrades and zero removals. General OS upgrades reserved for the later Security/Worker use case were not run. tailscaled was active/enabled, its state directory was root-owned with mode 0700, and a new public SSH connection and SSH syntax validation passed after installation. Runtime state was not copied into either repository. Enrollment, network authorization and cutover are separate checks below.

On the administration computer, the observed Manjaro package candidate was tailscale 1.102.3-1. The owner completed local installation and browser sign-in in their terminal; CLI version 1.102.3 and backend Running were then verified. The agent did not receive the local sudo password. Use the distribution package manager for another installation; do not refresh Arch/Manjaro repositories for a partial system upgrade merely to install this one package.

Use an interactive browser enrollment for the server rather than a reusable token in chat or shell history. Treat the enrollment URL as session material and do not commit it. Record successful enrollment without copying the daemon’s /var/lib/tailscale state into either repository. On the administration computer, select the documented package source for its actual Linux distribution rather than using the server’s Ubuntu repository.

Assign the VPS a server identity such as tag:haven after the policy permits its owner to apply that tag. Personal computers and phones retain user identities. On the verified 1.104.4 server, use tailscale up with the full existing preference set:

sudo tailscale up --advertise-tags=tag:haven --ssh=false \
  --accept-routes=false --accept-dns=false --hostname=haven-vps --timeout=10s

tailscale set --advertise-tags=…​ was rejected by this installed version before changing settings; up supports the flag. After the owner saved the policy, private SSH was unavailable until the permitted tag was assigned. The retained public SSH route allowed that transition.

Record the actual server node-key expiry. Initial authentication as a tagged server disables expiry by default, but changing tags on an already authenticated user-owned device does not necessarily change its existing expiry. The inspected node retained an expiration date, which was left unchanged and recorded privately. Revocation/re-enrollment after a lost or replaced device still needs an operating procedure.

Do not enable an exit node, subnet routing, Funnel or Tailscale SSH as part of this step. The required application path is the owner’s device to TCP 22 on this server.

Access policy and the host firewall

New tailnets can start with a broad allow-all policy. Review the full policy, remove unneeded broad rules, and grant the owner’s identity only the intended access. Grants add permissions; a narrow rule does not override a broad rule elsewhere.

The following is a synthetic example matching the verified policy structure. Substitute the real owner only in the private instance and validate the complete policy, including positive/negative tests, in the admin console before activation:

{
  "tagOwners": {"tag:haven": ["owner@example.com"]},
  "acls": [],
  "grants": [
    {
      "src": ["owner@example.com"],
      "dst": ["tag:haven"],
      "ip": ["tcp:22"]
    }
  ],
  "ssh": [],
  "tests": [
    {
      "src": "owner@example.com",
      "proto": "tcp",
      "accept": ["tag:haven:22"],
      "deny": ["tag:haven:80", "tag:haven:443", "tag:haven:40123"]
    }
  ]
}

The network policy grants reachability, not a Unix login. OpenSSH must still verify the administrator’s key and reject root/password login. Dashboard ports require separate grants when those services exist; the example does not expose them. The instance copy was saved with policy tests according to the owner; actual private SSH and port-denial checks independently confirmed the selected live paths.

Tailscale’s default Linux netfilter mode manages its own firewall rules, accepts tailnet traffic and can evaluate rules ahead of UFW. Therefore an apparently restrictive UFW interface rule alone is not the tailnet authorization boundary. Inspect the selected iptables/nftables integration on the actual host and enforce allowed users/ports in the tailnet policy. Keep the supported default integration unless a concrete tested requirement calls for another mode.

The inspected host’s IPv4 and IPv6 INPUT chains jump to ts-input before the UFW chains. ts-input accepts tailscale0 traffic and the Tailscale UDP transport. This ordering was read directly; tailnet access control was tested with a separate temporary listener rather than inferred from the UFW summary alone.

Cutover and recovery

Keep public SSH working during enrollment and policy validation. Before cutover, create a new root-only snapshot of the current hardened configuration and UFW state. The older pre-hardening backup intentionally contains the original password-enabled configuration and is not the right automatic recovery target for this operation.

A new verified backup of SSH/UFW, UFW defaults and daemon defaults was created on the inspected VPS. No Tailscale identity/runtime state was copied. Its root-only fallback script adds the public TCP 22 allowance without changing SSH authentication or disabling UFW. The owner confirmed both outstanding console/mobile checks before the timer was armed or public rules removed.

Keep an existing SSH transport open, verify the private path in a fresh connection and arm a host-side timed fallback before removing the public TCP 22 rule for both IPv4/IPv6. The fallback should restore the previous public SSH allowance while retaining key-only authentication, root-login denial and the active firewall. It must not invoke the earlier pre-hardening rollback or disable the whole firewall.

The executed fallback script used the following structure, saved under a new root-only backup directory with mode 0700. The example path is synthetic; use the actual installation’s backup path:

#!/bin/sh
set -eu
umask 077
/usr/sbin/ufw allow 22/tcp
/usr/bin/date -u +%FT%TZ > /root/haven-private-access-backup/PUBLIC_ACCESS_RESTORED.txt

After checking the script syntax, the guarded cutover used:

sudo systemd-run --unit=haven-tailscale-cutover-rollback --on-active=15m \
  --timer-property=AccuracySec=1s --property=Type=oneshot \
  /bin/sh /root/haven-private-access-backup/restore-public-ssh.sh
sudo systemctl is-active haven-tailscale-cutover-rollback.timer
sudo ufw allow in on tailscale0 to any port 22 proto tcp
sudo ufw --force delete allow 22/tcp
sudo ufw status verbose

The explicit UFW allowance is TCP 22 on tailscale0 for IPv4/IPv6. Tailscale’s own early rules and the tailnet policy remain part of the filtering path. Validate actual packet filtering rather than relying solely on the UFW summary. Make the cutover only after the computer and phone are enrolled, policy tests pass and the provider-console recovery route is verified.

If private access fails, use the retained public transport, timed fallback or provider console. Recover public reachability before stopping or reconfiguring Tailscale. In the exercised rehearsal, systemctl start haven-tailscale-cutover-rollback.service returned success, a fresh public key-based login worked, and key-only/root-denied SSH plus active UFW were preserved. The timer was restarted and public SSH removed again, followed by repeated private/public checks.

After final success, stop haven-tailscale-cutover-rollback.timer, confirm it is inactive, and close the maintenance transport. This was completed on the inspected host; a root-only receipt records the final checks. The recovery script remains available without an armed timer.

Acceptance

  • The intended server/computer/phone are enrolled, and the complete policy permits only the selected paths. Device/account names, addresses and versions are recorded privately.

  • A fresh OpenSSH connection from the owner’s computer succeeds over the private address/name with host-key checking and the existing administrator key. Verify the same host key before recording the new address as trusted.

  • The phone connects from a different network, preferably mobile data. If terminal administration is required, separately verify its SSH client/key; a Tailscale connection alone does not establish an SSH login.

  • A controlled listener confirms an unallowed tailnet port is denied even though the service answers locally. Verify policy denial for an unauthorized source using policy tests and an available independent test identity/device; record any unperformed live scenario.

  • After cutover, a fresh public SSH connection fails and a new private connection succeeds. Check IPv4 and IPv6 where connectivity permits, and document any untested path.

  • The timed public-access fallback is exercised and then cancelled after final checks. Service enablement/reconnection and a separate controlled reboot are verified; see bootstrap acceptance.

Verified private administration

Server version 1.104.4 and computer version 1.102.3 are connected; the phone is also reported online. Fresh administrator SSH connections use the established host-key identity and succeed over both private IPv4 and private IPv6. A temporary dual-stack TCP listener under the unprivileged service identity answered on loopback, while computer-to-server connections to that unallowed port timed out over both private address families. It served only a fixed marker and was stopped afterwards.

The owner confirmed provider-console login and phone connectivity with Wi-Fi disabled. Fresh private SSH connections passed over both address families after each cutover; root and password-only SSH attempts were rejected. The public IPv4 TCP 22 connection timed out after final closure. UFW and its IPv6 user rules were checked to retain only the tailscale0 SSH allowances. The original maintenance transport was closed after stopping the fallback timer, and a further fresh private connection succeeded.

An optional local OpenSSH alias can make the new path convenient while preserving the established host-key identity. This example must be adapted to the installation’s actual private address and previously trusted host name; do not overwrite existing host definitions:

Host haven
    HostName 100.101.102.103
    User ubuntu
    IdentityFile ~/.ssh/haven-admin
    IdentitiesOnly yes
    HostKeyAlias vps.example.invalid
    StrictHostKeyChecking yes
    UpdateHostKeys no
    ForwardAgent no

Back up the existing client configuration, validate it with ssh -G haven and test a fresh connection. The instance’s alias was verified after cutover; private values remain outside these public examples.

These checks accept the private-administration step with recorded limits. A live unauthorized-user scenario has not been run; policy tests cover the declared deny cases. Live public IPv6 was unavailable from the inspection computer, although its host rules were verified and private IPv6 SSH passed. The subsequent bootstrap/restart acceptance verifies return after reboot. Future key-expiry handling and the remaining H1 services are separate work.
