Wishlist: ordinary browser mode experiments

Status, 2026-11-06: bounded workstation follow-up to the direct-fetch probe. Both true headless Chromium modes returned HTTP 403 despite working JavaScript/cookies, including an exact-URL control. Fresh ordinary headed Chromium returned HTTP 200 and the expected product both on the desktop and on an authenticated temporary Xvfb display, without human verification. No VPS browser service or automatic fallback is deployed.

Executed experiment

Source baseline: f2c1a5b12d60a5fa0b69cc9f9c211ea10bb49c97. The sanitized receipt records versions, timestamps, source hashes, resource samples and limits. Private source C is the same operator-supplied product URL as in the initial probe; its URL, captures and full results stay outside public sources.

Playwright Python 1.64.1 launched Chromium 156.0.8078.4, revision 1248, first as Chromium Headless Shell and then as full Chromium with channel="chromium" in new headless mode. Each run had a fresh non-persistent context, JavaScript enabled, cookies available, downloads disabled and Chromium sandbox explicitly requested. No existing user profile, account login or exported storage state was used. Browser child environments contained temporary home/cache paths, language and executable path; the headed run also received display authorization metadata. The enclosing process had a 70-second deadline; navigation allowed 30 seconds and observation after DOM load lasted 20 seconds.

Browser evaluation confirmed working JavaScript and navigator.cookieEnabled. None of the contexts received a clearance cookie. The three headless runs stayed on the challenge through the 0/2/5/10/20-second checkpoints. The first runner’s English-only human-challenge boolean missed the Czech prompt; captured visible text and title established the result, and the retained runner adds the Czech marker. No interaction with the human-verification control was performed.

The owner reported that the exact original URL worked both in their regular browser and in a fresh private window without login. A headless control used that exact URL, including search parameters, and remained blocked. The ordinary headed comparison then succeeded in a new guest context with the same browser version and no custom identity overrides. This supports testing ordinary headed rendering separately from true headless mode; it does not identify the site’s exact decision rule or guarantee future access.

The headed page supplied the expected product identity and structured offer data. The generic extractor initially rejected the original URL’s extra search parameters as an identity mismatch. Offline comparison against the matching canonical product URL produced a candidate. A shop adapter must validate product identity before normalizing known tracking parameters. The page also exposed distinct public/member offers and a structured/display price rounding difference, so these candidates are not accepted deal observations yet.

The final comparison used Xvfb 21.1.24-1 from the configured Manjaro repository. Its package signature was verified with the system public keyring before extracting only the executable to the private temporary directory; no system package was installed. Xvfb used a temporary MIT-MAGIC-COOKIE-1 authorization file and -nolisten tcp, with a private display selected outside existing sockets. An outer wrapper ran the same fresh headed browser on that display and measured the combined tree. It obtained HTTP 200 and the same product candidate. The wrapper then terminated Xvfb and removed its display authorization file. This is a local Linux result, not an Ubuntu package/dependency acceptance.

Memory was sampled for the probe process and its descendants about every 150 ms using Linux /proc. For the first two runs, RSS peaks were 1148891136 and 1784356864 bytes respectively; summed RSS double-counts shared pages. PSS covered all sampled processes in the shell run, but some full-browser samples were incomplete. These are workstation observations, not guaranteed maximums or measurements on the VPS.

The workstation OS is outside Playwright’s officially supported systems, so its installer selected the Ubuntu 24.04 fallback build. This is another reason not to claim server acceptance from these runs. The two downloaded browser trees were roughly 273 MiB and 403 MiB; the separate Python environment was roughly 142 MiB. Only the experimental environment received packages.

VPS preflight

Read-only inspection found approximately 3.0 GiB available RAM and 2.0 billion free bytes on the filesystem containing /tmp. No browser or uv executable was present. The AppArmor unprivileged-user-namespace restriction was 1. unshare --user --map-root-user true failed while writing uid_map, exit 1.

No browser was installed or launched on the VPS, and no AppArmor, namespace or system setting was changed. This preflight identifies a sandbox prerequisite to investigate; it is not a direct Chromium startup test and does not establish what the target site would return to a VPS browser. Do not turn this workstation result into a production fetch-capability claim.

Reproduction inputs

The retained opt-in probe parameterizes temporary paths and accepts one reviewed target. It is a research runner, not a production network boundary. Its optional hash-pinned environment is separate from application/public-check dependencies. The first two measurements used the private runner; the exact-URL headless control used the prior retained runner and the two headed comparisons used a private variation, the last through an Xvfb wrapper. The current runner adds an explicit headed mode and was syntax/lint checked, not claimed as a sixth live run.

Prepare a fresh external working directory and a private one-element target JSON list. Set WISHLIST_BROWSER_WORK, WISHLIST_BROWSER_TARGETS and PLAYWRIGHT_BROWSERS_PATH explicitly. After installing the pinned optional environment, use python -m playwright install chromium --only-shell for the shell or --no-shell for full Chromium. Under a minimal environment, invoke python research/wishlist/browser_probe.py run-label or append chromium for full headless. Appending headed requires an authorized DISPLAY and XAUTHORITY; it opens and closes a separate window without using the owner’s profile. Run with an external process deadline as above. Raw HTML, screenshots and result files stay in the supplied private working directory; do not copy them into public sources or tests.

The generalized runner and lock are retained to make the next scoped experiment reviewable. Public checks never install or launch Playwright and never contact the source.

Consequence for collection

JavaScript/cookie support alone did not resolve this challenge in either tested headless mode. Cloudflare’s supported-browser documentation also excludes automated browsers from supported production challenge-solving environments. That describes platform support, not the exact site-specific trigger, which remains unknown.

Keep production fallback disabled pending a bounded source-access and sandbox design. Ordinary Chromium on Xvfb is now a locally demonstrated collection path, using windowed rendering without a physical desktop. The next experiment is an isolated Ubuntu/VPS browser with a working sandbox, a dedicated identity and resource limits. Source access from that IP, repeated collection, shop-price validation and recovery still need acceptance. A permitted product feed or a matching product at another approved source remain separate options.

An on-demand serial browser worker is now a concrete architectural option to validate. Its process, cookies, network and resource limits must be isolated from Nora and the domain database. These bounded observations do not justify an always-running browser or hosted-browser subscription by themselves.

Primary references: Playwright browser modes, launch options, browser contexts, challenge troubleshooting and Xvfb’s virtual-display model. Browser contexts separate cookies/storage, not operating-system permissions.
