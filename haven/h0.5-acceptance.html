H0.5 clean-checkout acceptance and H1 handoff

Historical acceptance record from before GitHub publication. Current repository, licensing and CI status is in H1.1.

Verified on 2026-10-25 on Manjaro Linux x86_64. The local H0 foundation is accepted: a fresh public clone can install its dependencies, validate configuration, create another synthetic private instance and build documentation using the documented workflow. GitHub publication/execution and live Ubuntu services remain pending.

Revision and environment

The working repositories still have no commits or remotes. To test a real clone, Git-eligible public files were copied into a disposable repository under /tmp, given one synthetic fixture commit and cloned with git clone --no-local. No working repository was committed, staged or pushed. The clone had no Git object alternates and started clean.

  • Fixture commit: ecba71a1d54d1901bbc1afce17f206b5c90b591f.

  • Fixture tree: 8441bbe5b7b909291b1b303813bf02d005806061.

  • Source manifest: SHA-256 for the 68 public input files, captured before this acceptance report and status updates were added. No configuration/runtime logic or dependency lock changed in H0.5; the documentation exporter gained two declared evidence attachments.

  • Structured result: versions, expected exit codes, installed Python packages and boundary checks. Fixture identifiers describe the disposable test source, not a published Haven revision.

Subprocesses received an allowlisted environment with a newly created home directory, empty package/configuration caches and no inherited account/authentication variables. Git system/global configuration and user package configuration were disabled or replaced with empty test locations. No original private files, project environments or user configuration were supplied to the cloned workflow.

Declared prerequisites were existing Python 3.12.14, Node.js 24.22.1 with npm 11.19.1, Git 2.55.0, a POSIX shell, sha256sum and system time-zone data. Project .venv, node_modules, tools and build output were absent from the snapshot and clone. They were created or downloaded afresh; no project environment or dependency cache was copied from H0.3/H0.4.

This is a fresh checkout and dependency installation on the existing host, not a clean operating-system, container or Ubuntu/VPS test. Installing the declared language/system prerequisites was outside the acceptance procedure.

Documented setup and checks

The first shell block in configuration setup and the first shell block in documentation tooling were extracted from the cloned guides and executed unchanged, in order. Their effective setup was:

python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes --only-binary=:all: -r requirements.txt
.venv/bin/python scripts/validate_config.py examples/instance.yaml
.venv/bin/python -m unittest discover -s tests -v
python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes --only-binary=:all: -r requirements-dev.txt
npm ci --ignore-scripts --no-audit --no-fund
.venv/bin/python -m scripts.install_check_tools
.venv/bin/python -m pip check
.venv/bin/python -m scripts.check

Both pip installs used the checked-in distribution hashes and binary-only policy. npm installed from the lock without lifecycle scripts. The binary installer downloaded Gitleaks/actionlint and verified their pinned archive hashes. pip check reported no broken requirements. No real credentials or private package registries were needed.

The complete checks passed before any private sibling existed: Ruff, strict yamllint, actionlint, configuration examples, all 23 behavior tests, all 16 retained H0.1 checksums, candidate-file and fixture-history secret scans, the Antora build and offline source/generated links. The initial site had 11 documentation pages plus its root redirect. H0.1 integration experiments were not rerun; their retained evidence was checked for integrity.

Another private instance

The instance-creation shell block in README was executed unchanged in the clone. It created a separate private Git repository from the public template. Its synthetic configuration was edited to use an independent instance name, time zone, reserved example hostname and placeholder model, then checked explicitly:

.venv/bin/python scripts/validate_config.py ../haven-private/config/instance.yaml
.venv/bin/python scripts/validate_config.py examples/instance.yaml \
  --override ../haven-private/config/instance.yaml

Both validations passed, and assertions confirmed the edited fields survived defaults/layering. Repeating the README setup exited with status 1 at its existing-destination check; hashes of every file in the synthetic private repository were unchanged. The public clone remained clean.

Ignore checks covered representative dotenv, authentication/session, credential, key and database paths in both repositories. Instance YAML was ignored by the public repository and remained eligible for the private repository. These checks establish the current Git rules, not encryption or runtime access controls.

Next, the synthetic private YAML was deliberately made invalid and given a synthetic marker. Running the complete public checks again still passed. The marker was absent from every generated site file, including attachments. The valid private YAML was restored afterwards. This complements the maintained tests for symlinks, escaping paths, undeclared targets and ignored inputs; it does not grant executors access to private data.

Live deployment acceptance in H1

The installation commands required no project changes. Only acceptance evidence, handoff/status documentation and the exporter’s two evidence-attachment declarations were added/updated. GitHub repository-name availability, the owner’s Haven license choice and the first actual Actions run remain open. No license was inferred from the retained upstream MIT material.

The first manifest format used file paths as JSON keys and triggered Gitleaks' generic API-key rule on an authentication-test log’s SHA-256. The retained manifest uses separate path and sha256 fields; the scan then passed without any rule exclusions or baseline.

Proceed to H1 prerequisites: choose infrastructure and backup storage, prepare the intended source/configuration revisions, confirm actual models/authentication and arrange the WhatsApp number/transport. Provisioning, interactive account authorization and production changes require their own authorized H1 work.
