H1 prerequisites and acceptance

H1 is in progress: publication is accepted, and administrator key access, the manual security baseline and configuration rollback were verified on Ubuntu 26.04 LTS on 2026-10-28. Tailscale private IPv4/IPv6 SSH, public-SSH cutover and narrow access fallback are verified. Bounded Ansible adoption, repeatability, access-file restoration and a controlled restart are also verified for the existing pilot. Native configuration, independent subscription login and one Hermes model request are verified. The bounded coordinator, native worker user bus, application rollback and restart/reboot recovery are verified. OS updates remain owner-deferred; coding dispatch stays disabled until H2. These are decisions and acceptance checks, not a complete clean-host installation procedure. H0.1 evidence retains its historical local/synthetic scope; WhatsApp remains unverified.

H1.6 owner-only Telegram text is accepted on the existing pilot: private enrollment, owner replies, denied-sender intake, blocked remote administration and enabled-service restart recovery are verified. The owner deferred WhatsApp, the second member and family sharing after confirming Agent Platform is unavailable on their account. The earlier Baileys/Agent Platform work remains inactive.

The owner subsequently selected H1.6.1 deterministic operations instead of ordinary AI chat. This profile is accepted with verified application rollback, idempotent repeat, restart and native execution guards. Four real owner messages produced two expected replies and two refusals without additional model calls or conversation rows; a live status reply after restart confirms transport recovery.

H0 handoff

H0.5 acceptance establishes the local foundation from a clean public clone with freshly installed dependencies. Configuration validation, instance creation and public documentation/checks work without the original private repository. The synthetic model and host are not deployment inputs, and the tested fixture commit is not a real Haven release.

Before reproducible deployment, establish the intended public-source revision and matching private configuration within the owner’s commit/remote authorization. Real source commits and separate public/private GitHub remotes now exist. The owner selected MIT; authenticated repository-name checks and publication are recorded in H1.1; automatic local push checks replace unavailable GitHub Actions with the owner’s agreement. These are distinct from the host/account acceptance below.

Owner choices before provisioning

  • Select a VPS and region within the agreed infrastructure budget. The first delivered host runs Ubuntu 26.04 LTS rather than the earlier 24.04 proposal. The pinned core/service is verified on this existing pilot; clean-host installation, broader integrations and the actual billing region still require verification.

  • Select an off-site backup destination, retention policy and recovery-key storage. Git does not back up sessions or databases.

  • Create the first Telegram bot through official BotFather and complete private token/owner enrollment. Do not obtain a dedicated WhatsApp number for this pilot. A later WhatsApp migration depends on actual eligibility then.

  • Select actual model identifiers and confirm authentication eligibility. The public model and hostname are placeholders. H1.4 verified the pilot’s selected model through live discovery and a native request; a subscription alone does not prove other integrations are supported.

Technical work and evidence required

Area Acceptance to establish in H1

Host

Document admin access, updates, firewall and service account; restrict internal services through the selected private access mechanism.

Hermes

Install the exact candidate and patch, translate Haven configuration to native inputs, supervise with systemd and survive a restart.

Credentials

Resolve references only for authorized services, reject missing credentials, and protect OAuth/WhatsApp runtime state outside Git.

Messaging and family access

Enroll eligible accounts privately, bind each connection to its verified owner, and test replies/restart recovery and negative cross-user access. Accept shared objects only after ownership/membership checks pass. Measure Czech voice quality and latency separately in H1.7.

Recovery

Exercise quota deferral/resumption and distinguish transient quota limits from revoked authentication; deterministic recovery must work without Nora’s model.

Backup

Restore the necessary configuration and runtime state on a clean target. Prevent a second simultaneously active WhatsApp session.

Documentation

Record the actually verified setup, interactive steps and recovery procedure without credentials, QR codes or session data.

Tailscale private administration and the bounded Ansible host playbooks are implemented and verified for the pilot. SOPS with age and restic remain proposed implementation choices. H0.3 only checks credential-reference syntax; it does not implement encrypted storage or runtime authorization.

The production controller/executor adapter belongs to H2. Deployment authorization and automatic rollback for the bounded demonstration target belong to H3. Passing foundation CI does not establish these runtime properties.
