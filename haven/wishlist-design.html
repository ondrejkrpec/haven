Wishlist: staged domain service design

Status, 2026-11-07: requirements and the modular Python direction are accepted. W1 domain state and W2 local service/Telegram ingress are implemented and tested locally; an extraction probe also exists. W5 wishlist conversation is implemented locally ahead of W3. The next minimum W4 slice covers deployment/recovery and live language acceptance, followed by W3 collection and remaining W4 acceptance. ADRs 0012 and 0013 record the boundaries. The deployed deterministic pilot remains unchanged.

First release

Accept product links through Nora’s owner-only Telegram interface, list and update private wishlist entries, record purchases, and collect price and availability observations once a day from supported supplied URLs. Start collecting history before cross-shop discovery or the complete H2 executor lifecycle.

Entries distinguish one-time purchases, recurring purchases and gifts for named recipients. A purchased one-time item or gift stops collection; a recurring item is paused for a configurable period, initially one month. Preserve historical observations. Infer classification from the user’s message where possible and ask when ambiguous; an incomplete classification must not discard the original link.

The initial user is the enrolled owner. Model per-entry ownership from the beginning, but keep additional Telegram users disabled until separate admission and cross-user denial checks pass. Each wishlist is private. Administrator access to the server/database is outside this application-level separation; no additional encryption against the server administrator is required.

Service and trust boundaries

Trusted Telegram ingress derives the principal and request identity. A bounded interpretation component may propose an operation and arguments; it cannot select another principal, write SQL, execute shell commands or grant permissions. The domain service authenticates callers, verifies ownership and validates every proposed operation. Confirm a write only after it commits; repeat delivery of the same Telegram request must not duplicate the write.

Use a modular Python service with a dedicated SQLite database. Keep wishlist entries, exact product identities, shop offers, price observations, collection runs and application events distinct. Prices retain currency, conditions, availability and observation time. Internal IDs and exact interfaces remain implementation work.

Only the service writes domain state. Collection jobs receive bounded offer/run inputs and submit results through a restricted result interface. They do not receive Nora’s credentials, personal context or arbitrary filesystem access. The current native model/tool/cron guard cannot be relaxed implicitly: first validate a separate bounded interpretation path against the pinned Hermes runtime. Local no-model commands remain usable if interpretation is unavailable.

No HTTP framework, broker, container topology or new YAML fields are selected by this design. Add only dependencies and configuration supported by an implemented need. Measure memory and concurrent work on the existing small VPS before deployment.

Offers and collection

Keep a global approved-shop registry plus per-entry shop permissions. A user-supplied URL from another shop grants collection scope only for that entry; it never edits the global registry. An unsupported shop may be saved with an explicit unsupported/pending collection status.

Track the exact linked product and variant. Preserve identity-bearing URL parameters while removing only verified tracking parameters. Additional acceptable variants are explicit user choices. Validate destinations and redirects, including resolved addresses, before fetching so submitted URLs cannot reach local/private services.

Prefer structured product data and small shop adapters. Bound response size, request duration, retries and concurrency. Website content is untrusted input. Distinguish ordinary prices from coupon, membership, quantity or variant-dependent offers. On failure retain the last valid observation with its original timestamp and show stale/failed collection; never invent a price or silently replace it with zero. Support must be demonstrated with direct fetches in the intended execution environment; browser/search-tool access is not sufficient acceptance.

Collection runs daily independently of the model. Persist the next due work and run outcomes so restart recovery is bounded and does not create duplicate observations for one run. Scheduling and single-run ownership still require a concrete design.

Later releases

Stage Scope

Cross-shop deals

Find the same product across approved shops; combine percentage and absolute savings with observed price history, offer conditions and availability. Show uncertainty while history is insufficient. Answer direct requests and send configurable interesting-offer summaries, initially every three days, with duplicate suppression.

Convenience

Explicit acceptable variants, optional read-only order-email ingestion, separately enrolled users and later task controls through Nora or the dashboard. Email matching must handle uncertain, cancelled and refunded orders; Gmail is outside the first release.

Security tasks

Introduce periodic read-only system/application/dependency checks and deduplicated Kanban findings, followed by isolated Worker/Reviewer execution and separately accepted bounded maintenance policies. Wishlist delivery does not depend on enabling coding tools.

Observability

Add searchable log aggregation, encrypted off-host archives with separate retention, and deduplicated issue creation from repeated errors. Logs are evidence, never execution authorization. A full ELK or self-hosted Sentry deployment is not selected.

The first release needs bounded structured logs, request/run correlation, health/freshness reporting and a read-only operational view. Audit application changes separately from diagnostic log retention. Daily observations stay in domain storage; repeated faults can later produce one Kanban issue. Agent reports and callbacks cannot bypass the existing controller/executor boundary.

Backup and acceptance

Extend the explicit backup capture policy for the new data and any new writer services; current H1 backup acceptance does not automatically include them. Define consistent capture, restore verification and schema/version compatibility before live use. Application rollback must not erase newly collected history.

Acceptance must demonstrate link intake, owner-scoped list/update, one-time completion, recurring pause, daily observations from supported shops, repeat-message idempotence, invalid variant/price rejection, safe destination handling, collection failure visibility and recovery after restart. Use synthetic public fixtures and isolated identities; keep real entries and account data outside public tests and documentation.

Live acceptance also verifies database restoration, dashboard freshness and no model calls from scheduled collection. No ordinary AI chat, coding dispatch, purchases, email access or host maintenance is enabled by this release.
