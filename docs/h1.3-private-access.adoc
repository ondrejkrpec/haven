= H1.3: Private administration with Tailscale

Status on 2026-10-28: researched rollout plan, not an installed or accepted integration. link:h1.3-first-access.adoc[Administrator SSH and the manual security baseline] are verified. The next target is a personal tailnet joining the VPS and the owner's computer/phone, followed by removal of public SSH access after acceptance.

== Intended result

Keep OpenSSH, the `ubuntu` administrator and existing key authentication. Tailscale provides the private network; Tailscale SSH is a different login mechanism and is not required for this rollout. The phone's Tailscale app provides connectivity; an SSH client with a separately managed key would additionally be needed for terminal administration from that phone. Later dashboards can use a browser over the tailnet after their own access rules are added.

Use the owner's personal account with protected sign-in and independent recovery material. Tailscale's current Personal plan is free for non-commercial personal use; verify eligibility and limits when enrolling. Keep login URLs, auth/API keys, node state, account identities and actual tailnet addresses outside public sources. Never give the runtime `haven` account or coding executors the administrator's SSH identity.

== Inputs and owner actions

* Create the personal Tailscale account and finish interactive identity-provider authentication. The operator cannot complete the owner's login or MFA on their behalf.
* Enroll the administration computer and phone into that same tailnet. On iOS, the owner installs the official app and approves its VPN configuration.
* Verify provider-console login, account recovery and a way to regain administration if the sole computer/key is lost before closing public SSH.
* Confirm the actual account identity and review the complete tailnet policy. Do not replace an existing network's policy without reviewing its other devices and required access.

== Staged installation

The official stable package page has an Ubuntu 26.04 `resolute` repository. Before changing the VPS, inspect its package candidate/version and an installation simulation. Follow the distribution-specific signed-keyring/repository instructions, record the exact installed version and changes, then enable the service. Add only the required Tailscale packages/dependencies after reviewing the simulation; a broad OS upgrade is a separate task. The owner reserved OS updates as a future Security/Worker test case.

Use an interactive browser enrollment for the server rather than a reusable token in chat or shell history. Treat the enrollment URL as session material and do not commit it. Record successful enrollment without copying the daemon's `/var/lib/tailscale` state into either repository. On the administration computer, select the documented package source for its actual Linux distribution rather than using the server's Ubuntu repository.

Assign the VPS a server identity such as `tag:haven`. Personal computers and phones retain user identities. Record the server's node-key expiry setting explicitly: tagged devices disable expiry by default. Revocation/re-enrollment after a lost or replaced device still needs an operating procedure.

Do not enable an exit node, subnet routing, Funnel or Tailscale SSH as part of this step. The required application path is the owner's device to TCP 22 on this server.

== Access policy and the host firewall

New tailnets can start with a broad allow-all policy. Review the full policy, remove unneeded broad rules, and grant the owner's identity only the intended access. Grants add permissions; a narrow rule does not override a broad rule elsewhere.

The following is a synthetic policy design, not an applied or server-validated file. Substitute the real owner only in the private instance, validate the complete policy in the admin console and add positive/negative policy tests before activation:

[source,json]
----
{
  "tagOwners": {"tag:haven": ["owner@example.com"]},
  "acls": [],
  "grants": [
    {
      "src": ["owner@example.com"],
      "dst": ["tag:haven"],
      "ip": ["tcp:22"]
    }
  ],
  "ssh": []
}
----

The network policy grants reachability, not a Unix login. OpenSSH must still verify the administrator's key and reject root/password login. Dashboard ports require separate grants when those services exist; the example does not expose them.

Tailscale's default Linux netfilter mode manages its own firewall rules, accepts tailnet traffic and can evaluate rules ahead of UFW. Therefore an apparently restrictive UFW interface rule alone is not the tailnet authorization boundary. Inspect the selected iptables/nftables integration on the actual host and enforce allowed users/ports in the tailnet policy. Keep the supported default integration unless a concrete tested requirement calls for another mode.

== Cutover and recovery

Keep public SSH working during enrollment and policy validation. Before cutover, create a *new* root-only snapshot of the current hardened configuration and UFW state. The older pre-hardening backup intentionally contains the original password-enabled configuration and is not the right automatic recovery target for this operation.

Keep an existing SSH transport open, verify the private path in a fresh connection and arm a host-side timed fallback before removing the public TCP 22 rule for both IPv4/IPv6. The fallback should restore the previous public SSH allowance while retaining key-only authentication, root-login denial and the active firewall. It must not invoke the earlier pre-hardening rollback or disable the whole firewall.

Retain any interface-specific SSH allowance required by the inspected firewall backend. Validate actual packet filtering rather than relying solely on the UFW summary. Make the cutover only after the computer and phone are enrolled, policy tests pass and the provider-console recovery route is verified.

If private access fails, use the retained public path, timed fallback or provider console. Recover public reachability before stopping or reconfiguring Tailscale. Once final checks pass, stop the fallback timer and retain the recovery procedure without credentials in the private runbook.

== Acceptance

* The intended server/computer/phone are enrolled, and the complete policy permits only the selected paths. Device/account names, addresses and versions are recorded privately.
* A fresh OpenSSH connection from the owner's computer succeeds over the private address/name with host-key checking and the existing administrator key. Verify the same host key before recording the new address as trusted.
* The phone connects from a different network, preferably mobile data. If terminal administration is required, separately verify its SSH client/key; a Tailscale connection alone does not establish an SSH login.
* A controlled listener confirms an unallowed tailnet port is denied even though the service answers locally. Verify policy denial for an unauthorized source using policy tests and an available independent test identity/device; record any unperformed live scenario.
* After cutover, a fresh public SSH connection fails and a new private connection succeeds. Check IPv4 and IPv6 where connectivity permits, and document any untested path.
* The timed public-access fallback is exercised and then cancelled after final checks. Service enablement/reconnection is verified; reboot recovery remains separately pending until tested.

The rollback and policy above are planned. Research and a valid documentation build do not establish installed Tailscale, successful enrollment or safe removal of public SSH.
