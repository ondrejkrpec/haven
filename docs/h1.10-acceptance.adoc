= H1.10: Operational acceptance of the existing pilot

Status, 2026-11-05: H1 is accepted for the existing single-VPS deterministic pilot. All eight steps have supported results, with earlier evidence explicitly identified below. The owner authorized completion of the remaining H1.10 work in one instruction on this date, replacing the earlier requirement to stop for a separate instruction between steps. H2 has not started.

== Accepted scope

H1.10 covers the existing single Ubuntu VPS and its link:h1.6.1-capabilities.adoc[deterministic Nora profile]. Telegram serves one enrolled owner through `system.status` and `system.capabilities`, including their explicit Czech aliases. Unknown requests and remote administration remain refused. The profile blocks ordinary model calls, tools and cron workers independently of the plugin hook.

The operational baseline includes the pinned Hermes runtime, systemd supervision, private SSH over Tailscale, owner-only static HTTPS documentation and a read-only dashboard. link:h1.9-backup-recovery.adoc[H1.9] supplies encrypted off-site backups, exact snapshot verification, isolated application recovery and independent external monitoring. Its earlier acceptance is evidence to review, not a new H1.10 test result.

== Deferred scope and later milestones

link:h1.7-czech-voice.adoc[Czech voice], WhatsApp and family sharing are owner-deferred and are not required passing scenarios for this pilot. Dashboard administration and ordinary AI chat remain disabled.

OS updates remain owner-deferred as a future Security/Worker scenario. H1.10 does not enable coding dispatch or grant workers administrator access. The isolated controller/executor adapter, role authorization and review lifecycle belong to H2; bounded autonomous repair/deployment belongs to H3.

A complete clean-host installation, another independent live instance and migration to macOS remain unverified. Acceptance of this existing pilot does not close the broader v0.1 requirements.

== Final combined acceptance, 2026-11-05

The fresh read-only revision audit matched the pinned Hermes source and the selected deployed files, native configuration, systemd definitions and dependency versions. The backup timeout fix was merged in https://github.com/ondrejkrpec/haven/pull/32[PR 32] and deployed through the explicit backup playbook under maintenance exclusion. Exact source pairs, hashes, timestamps and reproduction commands remain in private acceptance evidence.

Four new owner messages produced the two permitted operations and two refusals. The owner confirmed their replies; the private audit independently recorded the expected decisions with zero added usage. Automatic service recovery after a killed main process and a real host reboot passed. A new owner status reply after reboot confirms transport recovery. Aggregate model-call, token and cost counters remained unchanged throughout. Package and access-file hashes were unchanged by the reboot, and private web/snapshot, backup recovery and monitoring returned without manual service repairs.

A failed restore from 2026-11-03 had left one run awaiting reconciliation and one orphaned restic lock. Its exact host/PID and the absence of a live owner were checked before standard stale-lock removal. Full data verification and exact restoration then accepted the original snapshot; no upload was repeated. Fresh production backup and monitoring passed afterwards. The first failure's opaque exception does not establish its original cause. Separately, regression tests reproduced the controller's immediate kill on subprocess timeout; the fix gives SIGINT cleanup 20 seconds, reaps an unresponsive process and still fails the timed-out operation. It never clears locks or accepts snapshots automatically.

The current read-only HTTPS pages match their publication manifests; attempts to retrieve configuration or traverse outside the static roots are refused. Tailscale Serve retains the two private listeners without Funnel. Owner-only access inspection and earlier client acceptance do not establish a new test from another tailnet identity or public IPv6.

=== Reused evidence and limits

* H1.6/H1.6.1 supply the earlier live denied-sender and native sender/group/administration boundaries; their deployed code and configuration remain unchanged. The four owner operations and post-reboot response were tested afresh.
* H1.5 supplies the pinned synthetic quota/cooldown, terminal-authentication and restart-safe worker results: 107 passed and one Windows-only skip on the isolated Ubuntu run. These tests were reviewed rather than rerun or relabeled as a live subscription quota experiment. Coding workers remain disabled.
* H1.9 supplies the exact isolated application reconstruction, disaster discovery without a VPS receipt, operator/version recovery and owner-confirmed missed-heartbeat email. Current full-data checks, exact snapshot restores, backup freshness, timers, pause recovery and successful monitor runs were checked again.
* Billing/region records, independent recovery-material storage, Scaleway account MFA and broader clean-host/rescue/access scenarios remain explicit owner or future-work records. Actual provider quota exhaustion/revocation/refresh and every installed wheel byte remain unverified. No OS update, account enrollment, firewall change or expansion of model/worker permissions was performed.

This closes H1 for the accepted pilot. H2 must implement the controller/executor boundary, role authorization and review lifecycle before coding tools or delegated host maintenance can be enabled. H3 owns bounded autonomous deployment. A new VPS installation, another independent live instance and macOS migration remain outside this acceptance.
