= H1.6: private Telegram text

Status, 2026-10-29: the bounded implementation passes local synthetic acceptance. The separate Telegram runtime and disabled service guard/helper are prepared on the existing pilot; repeat deployment and application rollback pass. The owner selected Telegram for themselves only after confirming WhatsApp Agent Platform is unavailable on their account. Bot enrollment and live text/restart acceptance are pending.

== Bounded pilot

Hermes stays at v0.22.5, base `bf0203a794a07aac3ff764972ab9087baa4e4f4e`, with the existing attributed recovery patch. The native Telegram extra pins `python-telegram-bot[webhooks]==22.8`; the pilot uses only long polling. There is no public webhook, new firewall rule, third-party plugin or second gateway.

The optional Haven input is `telegram.enabled` and a quoted numeric `telegram.owner_id`. Disabled is the default; enabled requires exactly one owner. A username/display name is not an identity. The native profile has matching sender/private-chat allowlists, a nonmatching group sender sentinel, no guests/bots/group observation and no remote administrative principal. The permitted chat commands remain help/whoami/new/stop/status. Native Telegram intake rejects strangers and groups before event construction; the command gate and model tool restrictions remain separate.

CLI/local/API/cron/Telegram/WhatsApp model toolsets are empty. Coding dispatch, fallback, MCP/hooks, community plugins and lazy installs stay disabled. Automatic speech transcription is off; full attachment behavior and Czech voice quality are not accepted here. Strict outgoing media paths do not trust fresh arbitrary host files. Cold boot does not deliberately discard pending Telegram updates; this is not an exactly-once message-delivery guarantee.

The service explicitly disables first-contact profile building and predeclares the busy/tool-progress hints as seen. Those native hints otherwise write `onboarding.seen` into the guarded YAML after a message. They offer settings/tools outside this pilot, so they are suppressed rather than allowing arbitrary runtime configuration edits. The first-contact regression test exercises the actual pinned handler and confirms that the rendered profile remains unchanged.

== Prepare without activating

Use the checked public commit, pinned Ansible dependencies and explicit private inventory from link:h1.3-bootstrap.adoc[H1.3]:

[source,bash]
----
export ANSIBLE_CONFIG="$PWD/ops/ansible.cfg"
export ANSIBLE_HOME="$PWD/build/ansible"
.venv/bin/ansible-playbook -i ../haven-private/ops/inventory.yml \
  ops/telegram-prepare.yml -e haven_telegram_prepare_authorized=true
----

This checks the exact source and dependency hashes, builds `/var/lib/haven/telegram/venv` through upstream PM with only `--extra telegram`, verifies the real 22.8 import and protects prepared code as root-owned/read-only. Installation HOME/profile/cache are separate from production credentials. It neither changes the core environment nor enables messaging. The receipt permits repeat preparation with the same pins.

Render/deploy the updated service with both transports disabled using link:h1.5-service-recovery.adoc[the application procedure] before owner enrollment. The guard/helper/pin files belong to the bounded application snapshot; credentials, conversations and databases do not. The selected interpreter changes to the prepared Telegram environment only when Telegram is enabled. A missing model login still does not stop deterministic scheduling; an enabled messaging transport requires its own protected credential file.

== Owner enrollment

. Create a bot through official https://t.me/BotFather[BotFather] using `/newbot`. Keep the token private; do not put it in YAML, command arguments, chat or Git.
. In the owner's own terminal, run the installed helper over interactive SSH. It requires the disabled Telegram profile and refuses an existing token:

[source,bash]
----
ssh -t haven-example 'sudo -u haven /usr/bin/env \
  HERMES_HOME=/var/lib/haven/.hermes PYTHONPATH=/var/lib/haven/haven-tools \
  /var/lib/haven/telegram/venv/bin/python -m scripts.telegram_runtime enroll'
----

The helper prompts for the token without echo, verifies the bot and refuses an existing webhook. It prints a random one-time challenge in that local terminal. Send that exact text to the displayed bot from your own Telegram account. Only a matching challenge in a human sender's private chat can select the numeric owner. The helper saves the token in `/var/lib/haven/.hermes/credentials/telegram-bot-token` with directory `0700` and file `0600`, then prints only the verified owner ID and bot username. It neither calls the model nor sends chat messages. Keep other pollers stopped throughout enrollment.

Enter that ID in the private instance, render a fresh `--service` profile and deploy explicitly:

[source,yaml]
----
schema_version: 1
telegram:
  enabled: true
  owner_id: "123456789" # synthetic; use the locally verified owner ID
whatsapp:
  enabled: false
----

Do not reuse the synthetic ID. Startup validates policy, dependency hashes and credential metadata, then reads the token into a sanitized child environment. Native YAML and application rollback never contain it. Health requires the running gateway, fresh heartbeat and a connected Telegram adapter from the same process.

== Live acceptance

. Send a unique harmless text from the owner's private chat and verify one Nora answer without tools/fallback.
. Verify a denied principal cannot reach conversation/model handling. A separate account is optional: temporarily configure a different valid numeric owner ID, send from the now-denied actual owner, check connection plus aggregate session/model counters, and restore the accepted profile in cleanup even on failure.
. Verify admin commands cannot change models/configuration or run tools. Do not confuse a hidden command menu with authorization.
. Restart the managed service, verify it reconnects without token entry and send another unique text. Inspect replay/duplicate handling without assuming exactly-once external sends.
. Repeat deployment unchanged and retain a working application rollback. Never copy/delete the token or OAuth as a rollback step.

Do not run a second unmanaged gateway or `getUpdates` poller beside the service. After uncertain delivery, reconcile before resending. Revoke/rotate compromised bot tokens through BotFather with a deliberate disabled-profile replacement; enrollment refuses silent overwrite.
