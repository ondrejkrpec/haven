= H1.9: Off-site backup and recovery

Status, 2026-11-01: production encrypted backup, exact restore verification and independent monitoring are accepted on the Ubuntu pilot. A production snapshot passed full integrity and file/database restore checks. Its application profile was rebuilt in a fresh isolated Linux container with the pinned runtime, a different service UID/GID, unchanged production configuration, zero added model calls and no transport adapters. The owner confirmed the external missed-heartbeat email at 14:13:35 UTC. H1.10 remains the next overall operational milestone; a new VPS/OS provisioning cycle was not part of this recovery test.

The owner selected link:h1.9-scaleway-healthchecks.adoc[Scaleway Object Storage + Healthchecks.io]. link:adr/0011-trusted-backup-controller.adoc[ADR 0011] records the trusted controller and recovery boundary. Account secrets, exact snapshot/repository identities and operational receipts remain in the private instance.

== Services and authority

[cols="1,3",options="header"]
|===
|Component |Purpose
|`haven-backup.service` / `.timer` |Root-only consistent capture, encrypted upload, full repository check and exact snapshot restore. Runs at 02:00 and 14:00 UTC, with up to five minutes of jitter and persistent catch-up.
|`haven-backup-recovery.service` |Boot recovery of a pending pause and protected staging cleanup. `ExecStopPost` also recovers an interrupted backup. Recovery does not require backup settings or storage credentials.
|`haven-backup-health.service` |Fixed native read-only check as `haven`, with an empty capability set, strict filesystem protection and network denial. PID 1 starts it; the backup process needs no setuid helper or extra capabilities.
|`haven-monitor.service` / `.timer` |Five-minute independent check of native service health, dashboard freshness and the age of the last accepted backup. Its only writable filesystem path is the existing maintenance lock file.
|`haven-maintenance.service` |An explicit administrative exclusion lease. Application/backup deployment and operator retention use distinct transient leases holding the same lock.
|===

Trusted code and the hash-pinned restic 0.19.1 executable live in root-only `/usr/local/lib/haven-backup`. Secrets and rendered settings are under `/etc/haven-backup`; journals and private staging are under `/var/lib/haven-backup`. These paths are outside Nora's home and inaccessible to the service identity and future lower-trust workers. No operator/IAM administration key is deployed to the VPS.

The services do not depend on a model or Hermes cron. Healthchecks receives empty POST bodies over verified HTTPS, without redirects, proxy inheritance, source paths, command logs or conversation data. The link:https://healthchecks.io/docs/http_api/[ping API] confirms completion/start/failure; receipt of HTTP 200 alone is not proof that an email integration works.

== Captured state and consistency

The link:../examples/backup-capture.json[explicit capture policy] includes native configuration and required credentials, SQLite state/audit databases, sessions, Telegram receipts, memories, identity, schedules, skills and reviewed custom extensions. Missing optional board state stays absent. Source owners, groups, modes, mtimes and hashes are retained in an encrypted restore manifest alongside source revisions and the policy.

Named caches, installed Python/uv directories and transient sockets/PIDs/locks/heartbeats are excluded; pinned tool provenance remains. The reviewed `.clean_shutdown` marker exists only between stop and startup and is excluded explicitly. Restore treats interrupted activity conservatively instead of importing a live-process marker. New unknown paths, links, mount boundaries, unsupported metadata, unreviewed SQLite stores or missing required inputs stop capture. An unknown path is retained only in the protected journal, never stdout.

The controller verifies the existing repository identity before pausing. It holds `/run/lock/haven-maintenance.lock`, fsyncs the resume intent, stops the coordinator and requires no main process and an empty service cgroup. The pinned gateway can report exit 1 during stop; a failed unit state alone is not evidence of a remaining writer. A live/deactivating/nonempty cgroup is refused.

No-follow file descriptors anchor traversal and staging writes. The copy is checked against a second metadata pass. SQLite normalization operates only on the private copy, includes committed WAL state and verifies integrity. Cooperative capture limits are 256 MiB, 20,000 entries, depth 32 and 60 seconds; systemd separately bounds the whole job. The healthy coordinator resumes before network/archive work. A failed resume retains its durable intent and discards the copy.

== Snapshot acceptance and interrupted runs

A backup is accepted only after all of these succeed:

. Restic exits zero; exit 3 is an explicitly rejected incomplete snapshot.
. The full snapshot ID, repository identity, host and unique run tag match this run.
. `check --read-data` verifies repository data.
. The exact snapshot is restored with `--verify`; the complete file set, hashes, staging modes and SQLite integrity match its sealed manifest.

`accepted.json` records capture time rather than upload completion time. A success heartbeat follows acceptance. Credentials or storage failures before capture do not stop Nora. Handled failure and `ExecStopPost` clean private staging; boot recovery retries a pending resume. Synthetic stop/SIGKILL/real-systemd recovery and cleanup passed. Physical power loss was not simulated.

An uncertain upload is never repeated automatically and remote locks are not erased. Inspect its protected `run.json`, then use the explicit root operation:

[source,sh]
----
sudo env PYTHONPATH=/usr/local/lib/haven-backup \
  python3 -m scripts.backup_runtime reconcile
----

Reconciliation searches only that run's exact tag/host, verifies any completed snapshot and restores it before acceptance. No matching snapshot closes the interrupted run without creating a new backup. A failed integrity/restore check preserves the uncertainty for operator review.

== Install or update

Backup settings are separate operational inputs, not configuration v1. Start from link:../examples/backup-runtime.json[synthetic runtime metadata] in the private `ops/backup/runtime.json`; replace repository identity with the previously verified private receipt. Keep credentials in their enrolled directories outside Git.

`render_backup` requires clean public/private checkouts and a matching `HAVEN_REVISION`. It adds both exact source revisions at deployment time, avoiding a self-referential revision committed into its own inputs. From the public checkout:

[source,sh]
----
umask 077
haven_backup_render=$(mktemp -d)
.venv/bin/python -m scripts.render_backup /absolute/private-instance \
  --output "$haven_backup_render/settings.json"
ANSIBLE_CONFIG=ops/ansible.cfg ANSIBLE_HOME=build/ansible \
  .venv/bin/ansible-playbook -i /absolute/private-instance/ops/inventory.yml \
  ops/backup.yml -e haven_backup_authorized=true \
  -e "haven_backup_settings=$haven_backup_render/settings.json" \
  -e haven_backup_capture=/absolute/private-instance/ops/backup/capture-manifest.json \
  -e haven_backup_credentials=/absolute/private/scaleway-runtime \
  -e haven_backup_password=/absolute/private/restic-password \
  -e haven_backup_healthchecks=/absolute/private/healthchecks \
  -e haven_backup_restic=/absolute/public-checkout/build/h1.9/restic
----

Installation enables boot recovery and validates units without sending pings or enabling new timers. After live acceptance, the same playbook with `-e haven_backup_activate=true` enables backup and monitoring. It uses `no_log`/no diff for secret transfer. Repeating a deployment holds the maintenance exclusion while updating code and settings. OS updates, firewall, Tailscale and model permissions are outside this playbook.

Manual administrative commands must hold the common lock. For example:

[source,sh]
----
sudo flock -n /run/lock/haven-maintenance.lock systemctl restart haven.service
----

Never share another invocation's lease. A lost administrative session may leave a transient lease holding the lock; reconcile that exact lease before releasing it. Busy maintenance defers monitoring without forging success; prolonged silence still expires externally.

== Monitoring and retention

`haven-backup` has a 24-hour period/one-hour grace. `haven-service` has a five-minute period/five-minute grace and requires a fresh native heartbeat/dashboard plus a verified backup no older than 24 hours. The twice-daily schedule leaves room to recover from a failed backup. The owner confirmed the actual missed-service-heartbeat email; reporting was then restored. Telegram reply delivery is not measured by this monitor.

The VPS application key cannot delete data/snapshots or access previous object versions. A separate temporary operator key on the workstation handles recovery and retention. Versioning is a recovery layer, not immutable storage. A disposable encrypted repository was overwritten, its latest state failed integrity, older object versions restored the exact snapshot, and restoring the previous pack as the latest version repaired it. Runtime access to that separate prefix was denied; only recorded synthetic versions were cleaned up. IAM read-back also confirmed the runtime application's identity and preferred Project.

`scripts.backup_maintenance` obtains an exclusive VPS lease before a retention dry-run. It filters the production host/tag, groups by host, preserves the accepted snapshot and verifies the exact removal plan before `forget`/`prune`. Retention keeps seven daily/four weekly/three monthly recovery points. The real operator path passed without removing the accepted snapshot. Run it explicitly from the workstation with a newly enrolled operator key; no destructive retention timer or operator credential belongs on the VPS. Non-current provider versions require separately reviewed cleanup and can continue consuming storage.

== Restore to a new target

Obtain the independent repository password and private repository settings. The protected accepted receipt is useful when available; recovery must also work when the VPS and that receipt are lost. `scripts.backup_fetch --live` takes explicit settings, receipt, runtime credential/password directories and a new destination outside Git. It verifies repository/run/snapshot identity and restores exact bytes without starting software. With `--discover`, it reads the authenticated encrypted snapshot catalogue, pins a full ID, reads that snapshot’s authenticated manifest and verifies the complete restored file set. It does not contact the VPS or infer that a discovered candidate was previously accepted by the missing server. `--snapshot` can select a reviewed full ID if the newest candidate is incomplete. Temporary input-key copies are removed. Do not select mutable `latest` or overwrite an existing profile.

Rebuild dependencies from pinned public sources using upstream PM and its frozen lock. Use the pinned Python's SQLite: the base container's older SQLite rejected the production schema; the rebuilt Python 3.14.9/SQLite 3.53.1 passed. `scripts.backup_restore` verifies the sealed manifest, independently maps numeric UIDs/GIDs, restores executable/group modes and creates a new profile under a trusted owned parent. Place it at the final path only after admission checks. Restore Telegram delivery receipts before allowing the one production poller to connect.

The repeatable clean application recovery test uses an explicit public-only context:

[source,sh]
----
.venv/bin/python research/h1.9/container_context.py build/NEW-recovery-context
podman build --no-cache -t haven-recovery build/NEW-recovery-context
podman run --rm --network=none --security-opt=no-new-privileges --cap-drop=NET_RAW \
  -v /absolute/private-recovery-input:/recovery-input:ro \
  -v "$PWD/research/h1.9/container_restore.py:/opt/recovery/restore.py:ro" \
  haven-recovery /opt/recovery/restore.py
----

The input contains `accepted.json` and `restored/payload` from the fetch tool. The test verifies the exact production profile before boot, preserves that configuration and arms the independent deterministic guard. Only the disposable process's adapter factory is disabled before adapter construction; no Telegram poller or provider login is created. The core gateway/event-loop heartbeat becomes healthy, model-call totals stay unchanged and the read-only input is revalidated afterwards. This establishes clean application reconstruction, not a second production instance or a new Ubuntu host bootstrap.

== Evidence and recovery objectives

The first accepted production payload selected approximately 4.9 MB and passed encrypted off-site backup, full data check and exact file/database restore. The private receipts retain full snapshot/run IDs and code/image hashes. Fresh runtime dependency installation was measured separately, followed by isolated reconstruction and native startup; the observed application recovery is in minutes against a four-hour target. New VPS provisioning, owner enrollment and a physical host-loss exercise remain part of broader operational acceptance.

The 24-hour data-loss objective is enforced operationally by the 12-hour schedule and stale-backup alerts, not a guarantee during an unresolved provider outage. Keep the owner password manager, account recovery and private Git access independent of the VPS.
